# Lab 3c — baseline: หา host ที่ผิดจากเครื่องอื่นโดยไม่ใช้ signature (correlation แบบ 4)

**หัวข้อ** M6.2 (anomaly แบบไม่มี rule), M5.2 (สถิติจาก log), M6.4 (นิยาม "ปกติ" ขององค์กร) · **เวลา** 30 นาที · **ข้อมูล** Zeek conn 100k ใน HDFS · **ไม่ใช้ Spark** ทุกคำถามเป็น `hdfs_query_records` · **ควรทำหลัง lab 3** เพื่อเทียบว่าวิธีต่างกันเจอ host เดียวกันไหม

## โจทย์

lab 3 เริ่มจาก alert ของ Suricata ซึ่งต้องมีคนเขียน signature ไว้ก่อน lab นี้กลับทาง: **ไม่ดู alert เลย** ให้ Claude สร้าง baseline ว่าเครื่องปกติในเครือข่ายนี้ส่ง traffic ออกเท่าไร แล้วหาเครื่องที่ผิดจาก baseline นั้น นี่คือ correlation แบบ (4) ใน [glossary หมวด 6](../../docs/glossary.md#6-ฟังก์ชันของ-siem) ซึ่ง QRadar ทำด้วย Anomaly Detection Engine และ UBA ส่วนเราทำด้วยสถิติล้วน

ผู้เรียนต้องตัดสินใจเองว่า "ปกติ" วัดด้วยอะไร เพราะ metric ที่เลือกจะกำหนดว่าเจอหรือไม่เจอ

## สิ่งที่ต้องค้นให้ได้

คำถามข้างล่างคือสิ่งที่ analyst จะถามกันเมื่อเจอเรื่องนี้หน้า SIEM ผู้เรียนต้องตอบทุกข้อเป็นลายลักษณ์อักษร คอลัมน์ขวาบอกว่าคำตอบต้องมาจากผลของ tool ใด (ระบุชื่อ tool และฟิลด์ที่อ่านค่ามา) ไม่รับคำตอบที่ Claude สรุปให้โดยไม่มี tool รองรับ ข้อที่เป็นการตัดสินใจไม่มีคำตอบตายตัวแต่ต้องอ้างตัวเลขที่ค้นได้ คำตอบอยู่ในส่วนเฉลยด้านล่าง

| # | คำถามที่คุยกันใน SOC | ค้นจากอะไร |
| --- | --- | --- |
| 1 | ถ้าไม่มี signature เลย เครื่องนี้จะโดดออกมาให้เห็นไหม | baseline จาก Zeek conn โดยไม่แตะ alert (`hdfs_query_records` อย่างเดียว) |
| 2 | "ปกติ" ของเครือข่ายนี้คือเท่าไร วัดจากเครื่องกลุ่มไหน | ต่อเครื่อง: connection, byte ออก, byte เข้า, ปลายทาง distinct, พอร์ต distinct ของเครื่องกลุ่มผู้ใช้ (`cidr_filters`) |
| 3 | เครื่องที่แปลก แปลกตรงไหน มากกว่าหรือน้อยกว่าคนอื่น กี่เท่า | เทียบ metric แต่ละตัวของ host ที่สงสัยกับ baseline |

| 6 | ผิดจาก baseline แปลว่าร้ายไหม จะพิสูจน์ต่ออย่างไร และตรงกับที่ lab 3 เจอไหม | ฟิลด์ `interpretation` ของ tool + เทียบ host และ byte กับ lab 3 (วิธีอิสระ ไม่ใช่หลักฐานอิสระ) |


## ลำดับ tool ที่ควรเห็น

| # | tool | argument สำคัญ | ผลที่ต้องเห็น |
| --- | --- | --- | --- |
| 1 | `hdfs_query_records` | ไม่มี group_by, `distinct_fields` [id.orig_h, id.resp_h, id.resp_p, proto], `sum_fields` [orig_bytes, resp_bytes], `time_field` ts | ภาพรวมทั้งไฟล์: 201 host ต้นทาง, 207 ปลายทาง, 6 พอร์ต |
| 2 | `hdfs_query_records` | `group_by` [id.resp_p] + distinct id.orig_h | พอร์ต 80 มี 200 host; พอร์ตอื่นทั้งหมดมาจาก host เดียว |
| 3 | `hdfs_query_records` | `group_by` [id.orig_h], `max_groups` 100 | `groups_truncated: true`, 201 กลุ่ม แต่ได้มา 100 — **host ผิดปกติไม่อยู่ในนี้** |
| 4 | `hdfs_query_records` ×5 | `cidr_filters` {id.orig_h: 10.70.20.0/22}, …24.0/22, 28.0/22, 32.0/22, 36.0/22 | baseline ครบ 200 host ทีละ 40 |
| 5 | `hdfs_query_records` | `filters` {id.orig_h: [10.70.0.66]}, `group_by` [id.resp_p] | โปรไฟล์ของ host ที่สงสัย |

ขั้น 3 → 4 คือจุดที่ Claude ต้องรู้ข้อจำกัดของ tool: `max_groups` สูงสุด 100 (ขอ 201 จะได้ error `max_groups 1..100`) และกลุ่มเรียงตาม count มากไปน้อย ดังนั้น host ที่มี connection **น้อยกว่า** เครื่องปกติจะหลุดจาก 100 อันดับแรกเสมอ ต้องแบ่งถามด้วย CIDR

**ขั้น 1 — ภาพรวม** 100,000 conn, 2026-08-24 00:00:00 → 04:43:06 UTC (4 ชม. 43 นาที), orig_bytes รวม 11,690,870, resp_bytes รวม 207,560, 201 host ต้นทาง, 207 ปลายทาง, พอร์ต {22, 53, 80, 443, 445, 3389}, proto {tcp, udp}

**ขั้น 2 — แยกตามพอร์ตปลายทาง** (ขั้นเดียวก็เห็นแล้วว่าใครแปลก)

| 443 | 120 | **6,010,330** | 240 | 1 (10.70.0.66) | 1 (203.0.113.66) |
| 53 | 120 | 5,880 | 7,800 | 1 (10.70.0.66) | 1 (10.70.0.53) |

พอร์ต 443 มี 120 connection (0.12% ของทั้งหมด) แต่ byte ออก 6.0 MB มากกว่าพอร์ต 80 ที่มี 99,735 connection รวมกัน

**ขั้น 4 — baseline 200 host** (5 query ×40 host, รวม 99,735 conn = unmatched_right ของ lab 3 พอดี)

| metric ต่อ host | ค่าของเครื่องปกติ | การกระจาย |
| --- | --- | --- |
| connection | 498 หรือ 499 | 100 เครื่อง 499, 100 เครื่อง 498 |
| orig_bytes (ออก) | 28,331 – 28,388 | mean 28,369; ช่วงกว้างแค่ 57 byte |
| resp_bytes (เข้า) | 996 หรือ 998 | — |
| orig / resp | 28.4 | ทุกเครื่องเท่ากัน |
| ปลายทาง distinct | 9 | ทุกเครื่อง |
| พอร์ต distinct | 1 (80) | ทุกเครื่อง |

**ขั้น 5 — host 10.70.0.66** 265 conn: 443 → 203.0.113.66 ×120 (ทุก 10 s, stddev 0), 53 → 10.70.0.53 ×120 (ทุก 60 s, stddev 0), 22/445/3389 → 10.70.1.1–25 ×25 (ทุก 30 s ต่อพอร์ต)

**เทียบกับ baseline** — ตารางที่ผู้เรียนต้องทำเองได้

| metric | baseline | 10.70.0.66 | ผิดกี่เท่า | rule แบบ threshold จับได้ไหม |
| --- | --- | --- | --- | --- |
| connection | 498–499 | **265** | 0.53× (**น้อยกว่า**) | ไม่ได้ อยู่ใต้ baseline |
| orig_bytes | 28,369 | **6,017,085** | **212×** | ได้ |
| orig / resp | 28.4 | 744 (6,017,085 / 8,090) | 26× | ได้ |
| ปลายทาง distinct | 9 | 27 | 3× | ได้ |
| พอร์ต distinct | 1 | 5 | 5× | ได้ |
| ส่วนแบ่ง byte ออกทั้งเครือข่าย | 0.24% ต่อเครื่อง (1/201 ≈ 0.5%) | **51.5%** | — | ได้ |

**คำตอบของคำถามต่อยอด** ถ้าเรียงตาม connection 10.70.0.66 อยู่อันดับ **201 จาก 201** (ท้ายสุด) นี่คือเหตุผลที่ขั้น 3 ไม่เจอ และเป็นเหตุผลที่ rule "connection เกิน N ครั้ง" (correlation แบบ 2) ไม่มีวันยิงกับ host นี้ ส่วน rule เรื่อง byte (แบบ 4) ยิงทันที — metric ที่เลือกคือการตัดสินใจเชิง detection ไม่ใช่เรื่องเทคนิค

**ตรงกับ lab 3 ไหม** เจอ host เดียวกัน (10.70.0.66) และตัวเลขเดียวกัน (6,010,330 byte ไป 203.0.113.66:443) โดยไม่ได้แตะ alert เลย แต่**ไม่ใช่หลักฐานอิสระ** เพราะ Zeek conn กับ Suricata alert มาจาก PCAP เดียวกัน (lab 3 เตือนไว้: shared origin is not independent corroboration) สิ่งที่ได้คือ **วิธีอิสระ** สองวิธีให้ผลตรงกัน ซึ่งมีค่าคนละแบบ

## จุดที่คนต้องทำ

- **นิยามประชากร "ปกติ"** ก่อนคิดสถิติ: ที่นี่ใช้ 200 เครื่องในกลุ่ม 10.70.20–39.x ถ้ารวม 10.70.0.66 เข้าไปด้วย mean จะโดนลากขึ้นเป็น 58,163 (×2) และ stddev จะพังทันที — ใน SIEM จริงคือคำถามว่า baseline ต่อเครื่อง, ต่อแผนก (peer group) หรือต่อทั้งองค์กร
- **เลือก metric** และอธิบายว่าทำไม: byte ออก, อัตราส่วนออก/เข้า, จำนวนปลายทาง หรือหลายตัวรวมกัน ตารางข้างบนแสดงว่าตัวที่คนมักเลือกก่อน (connection count) เป็นตัวเดียวที่พลาด
- **ตั้ง threshold** 3σ, p99 หรือ "เกิน 10 เท่าของ median" ชุดนี้ baseline แคบมาก (57 byte) จนทุกวิธีให้คำตอบเดียวกัน ผู้เรียนต้องบอกได้ว่า**นี่คือลักษณะของข้อมูลสังเคราะห์** เครือข่ายจริงมี host ที่ backup ตอนกลางคืน, อัปโหลดวิดีโอ, sync cloud ซึ่งทำให้ 3σ ยิง FP ทั้งคืน และต้องมี baseline ตามชั่วโมงของวัน (QRadar เรียก Behavioral rule)
- **แยก "ผิดจาก baseline" ออกจาก "ร้าย"** tool คืน `interpretation: no incident verdict` ทุกครั้ง 6 MB ออกใน 20 นาทีอาจเป็น backup agent ก็ได้ ขั้นต่อไปคือ enrich ปลายทาง (lab 4) และดู payload (lab 3 ขั้น PCAP)
- **จดข้อจำกัดของ tool** ลงบันทึก: max_groups 100, เรียงตาม count, distinct กับฟิลด์ที่ไม่มีทุก record (เช่น `service`) จะ error ทั้ง query — ของจริงบน QRadar คือ AQL `GROUP BY` ที่มี limit และ `LIMIT` ที่ตัดผลเงียบ ๆ เหมือนกัน

## Claude ผิดตรงไหนได้บ้าง

- รายงานว่า "ไม่พบ outlier ทุกเครื่องส่งประมาณ 28 KB" จาก 100 กลุ่มที่ถูกตัด โดยไม่อ่าน `groups_truncated: true` — ให้ผู้เรียนถามว่า group_count เท่าไร ได้มาเท่าไร
- ขอ `max_groups` 201 แล้วเจอ error จึงลดกลับเป็น 100 และสรุปจากนั้น แทนที่จะแบ่งด้วย `cidr_filters`
- ใส่ `distinct_fields` ที่มี `service` → error `Missing field service at line 121` (เกิดจริงตอนรันเฉลย) แล้วบอกว่าไฟล์เสีย ทั้งที่กติกา tool คือ missing field fail ไม่ใช่เป็นศูนย์
- รายงาน z-score เป็นแสน ๆ ราวกับมีความหมาย ทั้งที่ stddev ของ baseline สังเคราะห์เกือบศูนย์ ตัวเลขนั้นบอกแค่ว่าข้อมูลถูกสร้างขึ้น ให้ใช้ "กี่เท่าของ median" แทนและบอกเหตุผล
- ข้ามไปสรุปว่า "exfiltration ยืนยันแล้ว" จาก baseline อย่างเดียว — baseline บอกว่า**ต่าง** ไม่ได้บอกว่า**ทำไม**
- บอกว่า lab 3 กับ lab 3c "ยืนยันกันและกัน" โดยไม่พูดถึง shared origin
