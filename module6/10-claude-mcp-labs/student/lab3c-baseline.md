# Lab 3c — baseline: หา host ที่ผิดจากเครื่องอื่นโดยไม่ใช้ signature (correlation แบบ 4)

**หัวข้อ** M6.2 (anomaly แบบไม่มี rule), M5.2 (สถิติจาก log), M6.4 (นิยาม "ปกติ" ขององค์กร) · **เวลา** 30 นาที · **ข้อมูล** Zeek conn 100k ใน HDFS · **ไม่ใช้ Spark** ทุกคำถามเป็น `hdfs_query_records` · **ควรทำหลัง lab 3** เพื่อเทียบว่าวิธีต่างกันเจอ host เดียวกันไหม

## โจทย์

lab 3 เริ่มจาก alert ของ Suricata ซึ่งต้องมีคนเขียน signature ไว้ก่อน lab นี้กลับทาง: **ไม่ดู alert เลย** ให้ Claude สร้าง baseline ว่าเครื่องปกติในเครือข่ายนี้ส่ง traffic ออกเท่าไร แล้วหาเครื่องที่ผิดจาก baseline นั้น นี่คือ correlation แบบ (4) ใน [glossary หมวด 6](../../docs/glossary.md#6-ฟังก์ชันของ-siem) ซึ่ง QRadar ทำด้วย Anomaly Detection Engine และ UBA ส่วนเราทำด้วยสถิติล้วน

ผู้เรียนต้องตัดสินใจเองว่า "ปกติ" วัดด้วยอะไร เพราะ metric ที่เลือกจะกำหนดว่าเจอหรือไม่เจอ

## ลำดับ tool ที่ควรเห็น

| # | tool | argument สำคัญ | ผลที่ต้องเห็น |
| --- | --- | --- | --- |
| 1 | `hdfs_query_records` | ไม่มี group_by, `distinct_fields` [id.orig_h, id.resp_h, id.resp_p, proto], `sum_fields` [orig_bytes, resp_bytes], `time_field` ts | ภาพรวมทั้งไฟล์: จำนวน conn, ช่วงเวลา, host ต้นทาง/ปลายทาง, พอร์ต |
| 2 | `hdfs_query_records` | `group_by` [id.resp_p] + distinct id.orig_h | พอร์ตใดมี host ต้นทางหลายตัว พอร์ตใดมาจาก host น้อยตัว |
| 3 | `hdfs_query_records` | `group_by` [id.orig_h], `max_groups` 100 | อ่าน `group_count` และ `groups_truncated` ก่อนสรุป — ได้มาครบทุกกลุ่มไหม |
| 4 | `hdfs_query_records` ×5 | `cidr_filters` แบ่งช่วง IP ให้แต่ละก้อนไม่เกิน 100 host | baseline ครบทุก host ทีละก้อน |
| 5 | `hdfs_query_records` | `filters` {id.orig_h: [10.70.0.66]}, `group_by` [id.resp_p] | โปรไฟล์ของ host ที่สงสัย |

ขั้น 3 → 4 คือจุดที่ Claude ต้องรู้ข้อจำกัดของ tool: `max_groups` สูงสุด 100 (ขอเกินจะได้ error `max_groups 1..100`) และกลุ่มเรียงตาม count มากไปน้อย ผู้เรียนต้องคิดเองว่า host แบบไหนจะหลุดจาก 100 อันดับแรก และจะถามอย่างไรให้ครบทุก host

## จุดที่คนต้องทำ

- **นิยามประชากร "ปกติ"** ก่อนคิดสถิติ: ที่นี่ใช้ 200 เครื่องในกลุ่ม 10.70.20–39.x ถ้ารวม 10.70.0.66 เข้าไปด้วย mean และ stddev จะเปลี่ยนไปมาก (ลองคำนวณทั้งสองแบบ) — ใน SIEM จริงคือคำถามว่า baseline ต่อเครื่อง, ต่อแผนก (peer group) หรือต่อทั้งองค์กร
- **เลือก metric** และอธิบายว่าทำไม: byte ออก, อัตราส่วนออก/เข้า, จำนวนปลายทาง หรือหลายตัวรวมกัน ตารางที่ทำเองในข้อ 7 จะบอกว่า metric ที่คนมักเลือกก่อนจับได้หรือไม่
- **ตั้ง threshold** 3σ, p99 หรือ "เกิน 10 เท่าของ median" ถ้า baseline แคบมากจนทุกวิธีให้คำตอบเดียวกัน ผู้เรียนต้องบอกได้ว่า**นี่คือลักษณะของข้อมูลสังเคราะห์** เครือข่ายจริงมี host ที่ backup ตอนกลางคืน, อัปโหลดวิดีโอ, sync cloud ซึ่งทำให้ 3σ ยิง FP ทั้งคืน และต้องมี baseline ตามชั่วโมงของวัน (QRadar เรียก Behavioral rule)
- **แยก "ผิดจาก baseline" ออกจาก "ร้าย"** tool คืน `interpretation: no incident verdict` ทุกครั้ง byte ออกจำนวนมากในเวลาสั้นอาจเป็น backup agent ก็ได้ ขั้นต่อไปคือ enrich ปลายทาง (lab 4) และดู payload (lab 3 ขั้น PCAP)
- **จดข้อจำกัดของ tool** ลงบันทึก: max_groups 100, เรียงตาม count, distinct กับฟิลด์ที่ไม่มีทุก record (เช่น `service`) จะ error ทั้ง query — ของจริงบน QRadar คือ AQL `GROUP BY` ที่มี limit และ `LIMIT` ที่ตัดผลเงียบ ๆ เหมือนกัน

## Claude ผิดตรงไหนได้บ้าง

- รายงานว่า "ไม่พบ outlier ทุกเครื่องส่งใกล้เคียงกัน" จาก 100 กลุ่มที่ถูกตัด โดยไม่อ่าน `groups_truncated: true` — ให้ผู้เรียนถามว่า group_count เท่าไร ได้มาเท่าไร
- ขอ `max_groups` เกิน 100 แล้วเจอ error จึงลดกลับเป็น 100 และสรุปจากนั้น แทนที่จะแบ่งด้วย `cidr_filters`
- ใส่ `distinct_fields` ที่มี `service` → error `Missing field service at line 121`  แล้วบอกว่าไฟล์เสีย ทั้งที่กติกา tool คือ missing field fail ไม่ใช่เป็นศูนย์
- รายงาน z-score เป็นแสน ๆ ราวกับมีความหมาย ทั้งที่ stddev ของ baseline สังเคราะห์เกือบศูนย์ ตัวเลขนั้นบอกแค่ว่าข้อมูลถูกสร้างขึ้น ให้ใช้ "กี่เท่าของ median" แทนและบอกเหตุผล
- ข้ามไปสรุปว่า "exfiltration ยืนยันแล้ว" จาก baseline อย่างเดียว — baseline บอกว่า**ต่าง** ไม่ได้บอกว่า**ทำไม**
- บอกว่า lab 3 กับ lab 3c "ยืนยันกันและกัน" โดยไม่พูดถึง shared origin
