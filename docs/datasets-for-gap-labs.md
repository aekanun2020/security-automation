# ข้อมูลสาธารณะจริงปิด lab G1–G6 ได้ครบ ยกเว้นส่วนที่เป็น QRadar-native

*รายงานสังเคราะห์จาก research notes สามชุด ข้อเท็จจริงทั้งหมดเก็บเมื่อ 2026-11-02 endpoint ที่ระบุว่า "LIVE" ถูกเรียกจริงด้วย `curl` ในวันนั้น ข้อมูล GitHub (license, last push, จำนวนไฟล์) ดึงจาก GitHub REST API หรือ `git clone --depth 1` สด ขนาดไฟล์ Zenodo มาจาก Zenodo records API*

**BLUF.** ทั้งหกช่องว่างมี dataset หรือ feed สาธารณะที่ **จริง เปิดใช้ได้ และ license เอื้อต่อห้องเรียน** รองรับอยู่แล้ว ยกเว้นสามสิ่งที่ไม่มีใครเผยแพร่เลย: QRadar offense export, SOC ticket export จริงที่มี ack/resolve + disposition และ LEEF corpus — สามสิ่งนี้ต้องสร้างแบบ parameterized synthetic จากตัวเลขรวมที่เผยแพร่ (Red Canary funnel 419M → 8.5M → 110k, NCSA 0.01% true attack / 49% benign trigger / 27% attempt, GUIDE 19/35/46 TP/FP/BP) แล้วตรวจกับ export จริงของผู้เรียนเองใน NT cyfence สำหรับ G1 แกนหลักคือ SecRepo `self.logs` (nginx จริง 2015–ต.ค. 2026, CC BY 4.0), Loghub Linux/OpenSSH (CC-BY-4.0 บน Zenodo) และ EVTX-to-MITRE-Attack (CC0, 293 ไฟล์ .evtx, อัปเดต พ.ค. 2026) G2 ใช้ Microsoft GUIDE (1.6M alert จริง, label TP/BP/FP, CDLA-Permissive-2.0) เป็นหลักและ AIT-ADS (2.66M alert, 96 MB, CC BY 4.0) เป็นตัวสำรองที่รันบน laptop ได้ G3 สร้าง lab แบบ **ไม่ต้องมี key เลย** ได้จาก CISA KEV + NVD + EPSS (แกน CVE), Feodo Tracker + Spamhaus DROP + Tor exit list (แกน IP), Shodan InternetDB, ip-api และ Tranco แต่ต้องรู้ว่า abuse.ch URLhaus/ThreatFox/MalwareBazaar บังคับ Auth-Key ตั้งแต่ 30 มิ.ย. 2025 และ URL เดิมคืน HTTP 410 แล้ว G4 ใช้ UCI ServiceNow incident log (24,918 incident, timestamps ครบ, CC BY 4.0) สอนกลไก MTTA/MTTR ควบกับ GUIDE สำหรับ FP-rate ต่อ detector G5 พร้อมที่สุด: SigmaHQ มี 3,161 production rule (2,817 รายการติด technique tag ครอบคลุม 391 technique) ภายใต้ DRL 1.1 และ IBM ดูแล `pySigma-backend-QRadar-AQL` (MIT, commit ล่าสุด 2026-10-29) ส่วน G6 ใช้ Loghub HDFS_v1/BGL ที่มี ground truth และเป็น benchmark ของ loglizer อยู่แล้ว สุดท้าย ผู้เรียนที่ "รัน QRadar ใน production" ปี 2026 ย่อมอยู่บน on-prem 7.5.x/7.6.x เท่านั้น เพราะ Palo Alto Networks ปิด QRadar on Cloud ไปเมื่อ 14 เม.ย. 2026 ดังนั้น lab ควร target REST API 28.0/29.0, header `SEC`/`Version`, LEEF ผ่าน syslog และ AQL — ทั้งหมดจำลองได้โดยไม่มี QRadar จริง หรือใช้ QRadar Community Edition (ฟรี, 100 EPS, 7.5.0 UP15 / 7.6 FP1) เป็นเครื่อง demo ของผู้สอน

### (b) ตัวเลือกหลักและสำรอง

Lab G1 ควรบังคับให้ผู้เรียนเจอ **สามรูปทรงของ log ที่ parser ปกติไม่รองรับ** และแต่ละรูปทรงมีของจริงรองรับ ตัวเลือกหลักคือ SecRepo `self.logs` สำหรับ combined access log เพราะเป็น production log จริงของ site ที่อัปเดตรายวันถึงปลาย ต.ค. 2026 ภายใต้ CC BY 4.0 ที่ประกาศชัดบนหน้าแรก และ manifest `data/site-links.json` ยืนยัน HTTP 200 ของทุก link เมื่อ 2026-06-06 ([secrepo.com](https://www.secrepo.com/); [site-links.json](https://www.secrepo.com/data/site-links.json)) คู่กับ Loghub Linux และ OpenSSH สำหรับ BSD syslog เพราะ Zenodo record 8196385 ให้ดาวน์โหลดตรงด้วย `?download=1` โดยไม่มี request form และระบุ license `cc-by-4.0` ([Zenodo 8196385](https://zenodo.org/records/8196385)) สำหรับ Windows ให้ใช้ EVTX-to-MITRE-Attack เพราะเป็นไฟล์ .evtx binary จริงที่ต้องผ่าน python-evtx หรือ `evtx_dump` ก่อน จึงใกล้สถานการณ์ "SIEM ไม่มี parser" ที่สุด และ README ยังอธิบายเองว่าออกแบบมาวัด SIEM coverage โดย agent เช่น WinCollect ส่งต่อได้ ([EVTX-to-MITRE-Attack](https://github.com/mdecrevoisier/EVTX-to-MITRE-Attack)) ส่วน JSON ใช้ CyberLab Cowrie ซึ่งมี schema ต่อ `eventid` (เช่น `cowrie.login.failed`) และ pseudonymise IP แล้ว ([Zenodo 3687527](https://zenodo.org/records/3687527))

ตัวสำรองคือ Harvard Dataverse nginx log (CC0, 274 MB) ถ้าต้องการไฟล์เดียวใหญ่ ๆ แทนไฟล์รายวันเล็ก ๆ ([Dataverse](https://dataverse.harvard.edu/dataset.xhtml?persistentId=doi:10.7910/DVN/3QBYB5)), sbousseaden/EVTX-ATTACK-SAMPLES แทน EVTX ชุดหลัก และ SecRepo `honeypot.json.zip` แทน CyberLab เป้าหมาย output ควรเป็น **LEEF 2.0 ที่มี `devTime` แบบ 13-digit epoch** (จึงไม่ต้องใส่ `devTimeFormat`) และ ECS 9.5.0 หรือ OCSF 1.9.0 (Authentication [3002], HTTP Activity [4002], Network Activity [4001]) ซึ่งทั้ง ECS และ OCSF เป็น Apache-2.0 และ repo ยัง push ล่าสุด ต.ค. 2026 ([ECS](https://www.elastic.co/docs/reference/ecs); [schema.ocsf.io](https://schema.ocsf.io/))

### (b) ตัวเลือกหลักและสำรอง

GUIDE เป็นตัวหลักเพราะเป็น **alert จริงจาก SOC ลูกค้าจริง** ที่มี `DetectorId` + `AlertTitle` ซ้ำกันข้าม 6.1k องค์กร และมี `IncidentGrade` สามค่า (TP/BP/FP) ที่ Region 2 กระจายประมาณ 14% TP / 34% FP / 52% BP ให้ใช้วัดว่า dedupe และ composite score ลดภาระโดยไม่ทิ้ง TP หรือไม่ ([arXiv 2407.09017](https://arxiv.org/html/2407.09017v4)) คอลัมน์ `MitreTechniques`, `Category`, `EntityType`, `Sha256`, `IpAddress`, `Url`, `AccountUpn` ยังทำ fingerprint ได้หลายระดับ (rule-only, rule+entity, rule+entity+org) ซึ่งเป็นแก่นของ lab นี้ ตัวสำรองคือ AIT-ADS ที่เหมาะกว่าสำหรับห้องเรียนที่เน็ตไม่ดีหรือเครื่องอ่อน เพราะทั้ง 2.66M alert อยู่ใน zip 96.2 MB และมี `labels.csv` บอกช่วงเวลา attack phase (scan, webshell upload, password cracking, privilege escalation, RCE, DNS exfiltration) ต่อ scenario ทำให้ alert นอกช่วงเป็น FP โดยนิยาม ([Zenodo 8263181](https://zenodo.org/records/8263181)) และ format เป็น Wazuh/Suricata JSON ที่คล้าย payload ที่ QRadar DSM ย่อยจริง

ตัวแปรให้คะแนน composite ควรดึงจาก feed ใน G3 (EPSS probability/percentile, CVSS baseScore, KEV membership, Feodo `c2_status`, DROP/Tor membership, AbuseIPDB `abuseConfidenceScore` 0–100, Tranco rank เป็นค่าลบ) และจาก rule metadata ใน G5 (Sigma `level` และ `falsepositives`, Elastic `risk_score` 0–100) เพื่อให้ score เดียวกันนำกลับไปใช้บน QRadar offense จริงได้ โดย map `DetectorId/AlertTitle` ↔ rule name และ composite score ↔ `magnitude`

### (c) ข้อควรระวัง

หน้า Kaggle ของ GUIDE เป็น JavaScript-rendered จึง **ยังไม่ยืนยันขนาดเป็น MB และข้อความ license บนหน้า** (CDLA-Permissive-2.0 มาจาก paper และ survey ปี 2026) ([arXiv 2605.08316](https://arxiv.org/pdf/2605.08316)) ผู้เขียน paper เองยอมรับว่า BP ไม่มีนิยามมาตรฐานและ ~81% ของ misclassification เกี่ยวกับ BP, ข้อมูลมาจาก region เดียว ช่วงเวลาสองสัปดาห์ และมีตารางที่ระบุ 46k graded incident ซึ่งไม่สอดคล้องกับตัวเลข 1M ([arXiv 2407.09017](https://arxiv.org/html/2407.09017v4)) paper ปี 2026 เพิ่มไฟล์ label สำหรับ queue ranking ต่อองค์กรบน Kaggle ([arXiv 2607.16963](https://arxiv.org/pdf/2607.16963)) AIT-ADS มีกลไกการติด "-" เป็น FP ที่หน้า Zenodo ไม่อธิบาย และ paper ปี 2026 หนึ่งฉบับรายงานตัวเลขต่อ IDS เล็กกว่ามาก (Wazuh 23,116 / Suricata 9,186) ซึ่งเป็น subset ให้ถือตัวเลข Zenodo เป็นหลัก ([arXiv 2609.02465](https://arxiv.org/pdf/2609.02465)) SALAD เผยแพร่ 2026-03-08 ยังไม่ได้อ่าน `datacard.md` จึงไม่ยืนยันว่ามีคอลัมน์ TP/FP ตรง ๆ

### (b) ตัวเลือกหลักและสำรอง

แกนหลักของ lab G3 ควรเป็นชุด **keyless ทั้งหมด** เพื่อให้ผู้เรียน 30 คนรันพร้อมกันได้โดยไม่ต้องสมัครอะไร: แกน CVE ใช้ KEV + NVD + EPSS ซึ่งทดสอบจริงแล้วว่า NVD call เดียวคืนทั้ง CVSS 3.1 (CVE-2020-29583 = 9.8 CRITICAL) และฟิลด์ `cisaExploitAdd`/`cisaActionDue` ([NVD](https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2020-29583)) และ EPSS คืน `epss` 0.99999 / percentile 1.0 สำหรับ CVE-2021-44228 ([EPSS](https://api.first.org/data/v1/epss?cve=CVE-2021-44228,CVE-2020-29583)) แกน IP ใช้ Feodo (CC0 ตามข้อ 3.4 ของ abuse.ch Terms) + Spamhaus DROP + Tor exit list ซึ่งทั้งหมดดาวน์โหลดเป็นไฟล์ได้ครั้งเดียวแล้ว hit-test offline ([abuse.ch ToU](https://abuse.ch/terms-of-use/); [DROP](https://www.spamhaus.org/drop/)) เสริมด้วย InternetDB (exposure), ip-api (geo, 45/min) และ Tranco (benign rank) การฝึก retry และ rate-limit ให้ใช้ ip-api เป็นตัวสาธิตเพราะคืน header `X-Rl`/`X-Ttl` ชัดเจนและตอบ 429 เมื่อเกิน ([ip-api docs](https://ip-api.com/docs/api:json)) และใช้ Spamhaus เป็นตัวสาธิต caching เพราะห้าม fetch เกินชั่วโมงละครั้ง

ตัวสำรอง (ต้องสมัคร key ฟรีรายคน) คือ AbuseIPDB ที่ให้ 1,000 check/วัน และคืน `abuseConfidenceScore` 0–100 ที่ normalise แล้ว ([AbuseIPDB docs](https://docs.abuseipdb.com/)), VirusTotal Public (500/วัน, 4/นาที) ([VT docs](https://docs.virustotal.com/reference/public-vs-premium-api)) และ OTX ที่ทดสอบจริงแล้วว่า indicator lookup ตอบ 200 โดยไม่ส่ง `X-OTX-API-KEY` ([OTX](https://otx.alienvault.com/api/v1/indicators/IPv4/8.8.8.8/general)) ส่วน URLhaus/ThreatFox/MalwareBazaar ควรเป็น optional module ที่ให้ผู้เรียนสร้าง Auth-Key เองผ่าน auth.abuse.ch ([abuse.ch Community First](https://abuse.ch/blog/community-first/))

### (b) ตัวเลือกหลักและสำรอง

เลือก UCI ServiceNow log เป็นตัวหลักเพราะเป็นข้อมูล **audit จริงจาก ServiceNow** ที่มี timestamp ครบวงจร `opened_at → sys_created_at → resolved_at → closed_at` พร้อม `priority` (impact × urgency), `made_sla` และ `reassignment_count` จึงคำนวณ MTTA-like, MTTR, weekly rollup, SLA-breach % และ reassignment churn ได้ตรง ๆ ด้วย pandas ([UCI 498](https://archive.ics.uci.edu/dataset/498/incident+management+process+enriched+event+log)) จุดอ่อนคือไม่มี rule name และ disposition จึงต้องควบกับ GUIDE ซึ่งให้ **FP-rate ต่อ `DetectorId`** และ volume ต่อองค์กรต่อวันจาก alert จริง ([arXiv 2407.09017](https://arxiv.org/html/2407.09017v4)) ผลลัพธ์คือ lab สอง pipeline: lifecycle metrics จาก UCI และ rule-quality metrics จาก GUIDE แล้ว render รายงานรายสัปดาห์ร่วมกัน

ตัวสำรอง (และเป็นตัวที่ใกล้ QRadar ที่สุด) คือ **synthetic offense/ticket generator แบบ parameterized** ซึ่งซื่อตรงกว่าการแกล้งว่ามีข้อมูลจริง: ใช้ funnel ของ Red Canary ปี 2025 (419M investigative leads → 8.5M potentially malicious events → 110,000 confirmed threats, 34,000 higher-severity, จาก 1,700 องค์กร) ([Red Canary methodology](https://redcanary.com/threat-detection-report/methodology/)), สัดส่วน NCSA (0.01% true attack / 49% benign trigger / 27% attack attempt จาก 115M alert ใน 4 ปี) ([USENIX Sec 2024](https://www.usenix.org/conference/usenixsecurity24/presentation/yang-limin)) และสัดส่วน TP/FP/BP ของ GUIDE เป็น prior ของ disposition ส่วนการกระจายของเวลา resolve ให้ fit จาก UCI แล้วใช้ VCDB เป็นบริบทว่าค่า discovery/containment ในอุตสาหกรรมเป็นหลักวันหรือเดือน ([VCDB](https://github.com/vz-risk/VCDB)) schema เป้าหมายควรยึดคอลัมน์ขั้นต่ำของ QRadar offense (ID, Description, Offense Source, Magnitude, Severity, Start Time, Last Updated, Assigned To, Status, Closing Reason) เพื่อให้โค้ด metrics รันบน export จริงของผู้เรียนได้ไม่ต้องแก้

### (c) ข้อควรระวัง

หน้า UCI **ไม่ระบุช่วงเวลาของข้อมูล** และคอลัมน์ QRadar offense CSV เป็นสิ่งที่ผู้ใช้เลือกตอน export จึงต้องกำหนดรายการคอลัมน์มาตรฐานใน lab ([IBM Exporting offenses](https://www.ibm.com/docs/en/SSKMKU/com.ibm.qradar.doc/t_qradar_export_off.html)) ฟิลด์ของ `GET /siem/offenses` (epoch ms, `closing_reason_id`, `credibility`, `relevance`) ยืนยันได้จาก GitHub-Pages snapshot ของ API 23.0 แต่ยังไม่ได้ตรวจกับ `/api_doc` บน Console จริงของผู้เรียน VCDB ตัด source folder หนึ่งออกจาก CSV เพื่อลด bias ([VCDB NOTE.txt](https://raw.githubusercontent.com/vz-risk/VCDB/master/data/csv/NOTE.txt)) และ Expel/Red Canary ไม่เผยแพร่การกระจาย MTTA/MTTR ที่ใช้ parameterize ได้ตรง ๆ (หน้า Expel ดึงได้แต่ชื่อเรื่อง)

### (b) ตัวเลือกหลักและสำรอง

ตัวหลักคือสาย **SigmaHQ/sigma → sigma-cli 4.0.0 → `ibm-qradar-aql`** เพราะครบทั้งสามส่วนของ lab: rule YAML ที่ vendor-neutral ภายใต้ DRL 1.1 ซึ่งอนุญาตใช้และแก้ไขพร้อม attribution ([Sigma LICENSE](https://github.com/SigmaHQ/sigma/blob/master/LICENSE); [DRL](https://github.com/SigmaHQ/Detection-Rule-License)), การแปลงเป็น AQL ด้วยคำสั่งเดียว `sigma convert -t ibm-qradar-aql -p qradar-aql-payload rules/windows/...` ที่ให้ output เช่น `SELECT * FROM events WHERE devicetype=12 AND LOWER("Target Process Path") LIKE '%\keepass.exe'` ([IBM backend README](https://github.com/IBM/pySigma-backend-QRadar-AQL)) และการวัด coverage ด้วย `sigma analyze attack` ที่เขียน Navigator layer 4.4 โดยกรอง `--min-level`/`--min-status` ได้ ([sigma-cli analyze.py](https://github.com/SigmaHQ/sigma-cli/blob/main/sigma/cli/analyze.py)) backend ของ IBM ต้องการ content pack "Properties Dictionary" บน QRadar และมี pipeline สองแบบ ผู้เรียนควร diff output ของ `-fields` กับ `-payload` และนับจำนวน field ที่ไม่ map ได้เป็นส่วนหนึ่งของ "coverage" เพราะ payload pipeline ไม่รองรับ Boolean/Null/CIDR/regex/numeric comparison

README ของ loglizer ยังเขียนว่าต้อง "submit your access request" ซึ่งล้าสมัยแล้วเพราะ Zenodo เปิดหมด ([loglizer](https://github.com/logpai/loglizer)) ยังไม่ได้ทดสอบว่า loglizer master รันบน Python 3.12 สะอาดหรือไม่ label ของ Hadoop ติดธง issue #56 ที่ไม่ได้อ่านเนื้อหา SR-BH มี blog เชิงโปรโมตปี 2026 อ้างว่ามี benign row ถูก label ผิด ([Cyshield blog](https://seclab.cyshield.com/posts/augmenting-sr-bh-2020-a-technical-methodology-for-modern-threat-simulation/)) AIT-LDS เป็น CC-BY-NC-SA จึงห้ามใช้ในหลักสูตรที่คิดค่าเรียนเชิงพาณิชย์โดยไม่ขออนุญาต และ UNSW-NB15 ระบุ "Commercial use must be agreed with the authors" ([UNSW-NB15](https://research.unsw.edu.au/projects/unsw-nb15-dataset)) honeypot data เป็น hostile 100% จึง "anomaly" label ไร้ความหมายสำหรับ precision/recall

### LEEF: IBM เผยแพร่ตัวอย่างบรรทัดครบพอใช้เป็น unit-test fixture

เอกสาร DSM ของ IBM นิยามโครงสร้าง `[syslog header] LEEF:<ver>|Vendor|Product|Version|EventID|[Delimiter|]key=value<TAB>key=value…` โดย syslog header เป็น RFC 3164 (`<13>Jan 18 11:07:53 192.168.1.1`) หรือ RFC 5424 (`<13>1 2019-01-18T11:07:53.520Z 192.168.1.1`, `<133>1 2019-01-18T11:07:53.520+07:00 myhostname`) และให้ตัวอย่าง header จริง **`LEEF:1.0|Microsoft|MSExchange|4.0 SP1|15345|`**, **`LEEF:2.0|Lancope|StealthWatch|1.0|41|^|`**, `LEEF:2.0|Vendor|Product|Version|EventID|x5E|` และ `LEEF:1.0|Microsoft|MSExchange|2007|Logon Failure|` พร้อม attribute ตัวอย่าง `src=192.0.2.0 dst=172.50.123.1 sev=5 cat=anomaly srcPort=81 dstPort=21 usrName=joe.black` ([IBM LEEF event components](https://www.ibm.com/docs/en/dsm?topic=overview-leef-event-components)) LEEF 2.0 เพิ่มฟิลด์ delimiter ที่เป็นตัวอักษรเดียวหรือ hex แบบ `0x`/`x` + 1–4 หลัก (default คือ tab), EventID ยาวไม่เกิน 255 ตัวอักษร, ต้องเป็น UTF-8 และ "QRadar cannot route IPv6 addresses" ใน syslog header attribute ที่ QRadar ใช้ normalise ได้แก่ `cat` (ขยาย EventID สำหรับ QID mapping), `devTime` + `devTimeFormat` (ไม่ต้องใส่ format ถ้า devTime เป็น epoch 10/13 หลัก), `proto`, `sev` (1–10), `src`/`dst`, `srcPort`/`dstPort`, `*PreNAT/*PostNAT`, `usrName` (≤255), `srcMAC/dstMAC`, `identSrc/identHostName`, `accountName`, `srcBytes/dstBytes`, `url`, `domain`, `policy`, `resource` ([IBM predefined LEEF attributes](https://www.ibm.com/docs/en/dsm?topic=overview-predefined-leef-event-attributes)) QRadar รับ LEEF ทาง syslog หรือ Log File Protocol และ **ต้องเห็นประมาณ 25 event ก่อน auto-discover log source** (ก่อนนั้นจัดเป็น "SIM Generic Log DSM"/"Unknown Log Event") และหลัง 1,000 event ที่ระบุไม่ได้จะหยุด auto-detect ([IBM LEEF overview](https://www.ibm.com/docs/en/dsm?topic=leef-overview)) ดังนั้น emitter ของ lab ควรส่งเป็น batch ≥ 25 บรรทัดโดยคง Vendor|Product เดิม ใช้ `LEEF:2.0|<Course>|<Tool>|1.0|<EventID>|x09|` และ `devTime` เป็น epoch ms แล้วเพิ่ม custom key สำหรับ enrichment (`epss=`, `kev=true`, `abuseScore=`) ตัวอย่างบรรทัดเดี่ยวเพิ่มเติมอยู่ที่เอกสาร NXLog ([NXLog LEEF](https://docs.nxlog.co/integrations/format/leef.html)) และ CEF อ้างอิงจาก OpenText "CEF Implementation Standard" ที่มีตัวอย่าง `CEF:0|Security|threatmanager|1.0|100|worm successfully stopped|10|…` ([CEF PDF](https://www.microfocus.com/documentation/arcsight/arcsight-smartconnectors-24.1/pdfdoc/cef-implementation-standard/cef-implementation-standard.pdf))

### REST API: header `SEC` + `Version`, paging ด้วย `Range`, แผนที่เวอร์ชัน 7.5.0 → 17.0, UP15 → 28.0, 7.6.0 → 29.0

หน้า getting-started ของ IBM ยืนยันว่า API เรียกผ่าน HTTPS ไปที่ Console ด้วย GET/POST/PUT/DELETE, auth ที่แนะนำคือ **authorized-service token ใน header `SEC`** (basic auth รองรับเฉพาะหน้า documentation), header **`Version`** ใช้ semantic versioning (`3` → 3.x ล่าสุด, `3.0` ตรงตัว, ไม่ใส่ → ล่าสุดซึ่งอาจพังหลัง upgrade), endpoint ที่ deprecated คืน header `Deprecated` และคงไว้อย่างน้อยหนึ่ง release, ที่ถูกถอดคืน 410, เวอร์ชันที่ไม่รองรับคืน 422, query param `filter`/`sort` และ paging ผ่าน header `Range` ([IBM REST API getting started](https://www.ibm.com/docs/en/SS42VS_SHR/com.ibm.qradarapi.doc/c_rest_api_getting_started.html)) ตารางเวอร์ชันระบุ **QRadar 7.6.0 → API 29.0** (รองรับ 28.0/27.0/26.x ด้วย), **7.5.0 UP15 → 28.0**, 7.5.0 → 17.0, 7.4.0 → 13.0 เอกสารสาธารณะแบบ static บน GitHub Pages มีถึง API 23.0 เท่านั้น (`https://ibmsecuritydocs.github.io/qradar_api_20.0/` ถึง `_23.0/` ตอบ 200 ทั้งหมด) ซึ่งระบุว่า `POST /ariel/searches` สร้าง search แบบ async รับเฉพาะ SELECT, window default 60 วินาทีสุดท้าย, คืน 201 กับ `search_id` และ `status` ∈ WAIT|EXECUTE|SORTING|COMPLETED|CANCELED|ERROR (422 code 2000 = AQL ผิด, 503 = Ariel offline) ([POST /ariel/searches 23.0](https://ibmsecuritydocs.github.io/qradar_api_23.0/23.0--ariel-searches-POST.html)) และ `GET /siem/offenses` รับ `fields=id,description,magnitude`, `filter`, `sort` และ header `Range: items=50-99` (zero-indexed) โดย offense object มี `status (OPEN|HIDDEN|CLOSED), magnitude, severity, credibility, relevance, offense_type, offense_source, start_time, last_updated_time, close_time` (epoch ms), `closing_reason_id, event_count, flow_count, rules[{id,type}], log_sources[{id,name,type_name}]` ([GET /siem/offenses 23.0](https://ibmsecuritydocs.github.io/qradar_api_23.0/23.0--siem-offenses-GET.html)) mock server ของห้องเรียนจึงต้อง implement ให้ตรงสี่จุด: `POST /api/ariel/searches?query_expression=…` → `{search_id, status:"WAIT"}`, `GET /api/ariel/searches/{id}` ที่ไล่ status จนถึง COMPLETED, `GET /api/ariel/searches/{id}/results` → `{"events":[…]}` และ `GET /api/siem/offenses` ที่เคารพ `Range`/`filter`/`fields` โดยทุก endpoint ต้องการ header `SEC` และ `Version: 28.0` repo ของ IBM ที่ยังมีชีวิตและขุด JSON shape ได้คือ `IBM/qpylib` (push 2026-09-28), `IBM/qradar-mcp` (2026-11-01), `IBM/qradar-misp-ioc-importer` (2026-01-25) ส่วน `IBM/api-samples` archived ตั้งแต่ 2020 ([GitHub search](https://api.github.com/search/repositories?q=qradar+org:ibm-security+org:IBM))

### AQL: โครงสร้างยืนยันจาก IBM แต่ตัวอย่างคำสั่งจริงดึงไม่ได้

หน้า AQL ของ QRadar 7.5 ยืนยันโครง `SELECT … FROM events|flows [WHERE] [GROUP BY] [ORDER BY] [LIMIT]` กับ time clause `LAST n MINUTES|HOURS|DAYS` หรือ `START … STOP …`, ฟิลด์ทั่วไป `sourceip, destinationip, destinationport, username, qid, starttime, magnitude` และฟังก์ชัน `QIDNAME(qid)`, `LOGSOURCENAME(logsourceid)`, `CATEGORYNAME(category)`, `DATEFORMAT`, `UTF8(payload)`, `TEXT SEARCH`, `REFERENCESETCONTAINS` ([IBM AQL 7.5](https://www.ibm.com/docs/en/qsip/7.5?topic=aql-ariel-query-language)) แต่หน้า "Sample … AQL statements" และ PDF `b_qradar_aql.pdf` คืน 403 จึง **ไม่มี AQL ตัวอย่างแบบ verbatim จาก IBM ในรายงานนี้** แหล่ง AQL ที่ valid เชิง syntax และดึงได้คือ output ของ `IBM/pySigma-backend-QRadar-AQL` (เช่น `SELECT * FROM events WHERE devicetype=12 AND LOWER("Target Process Path") LIKE '%\keepass.exe'`) และ sample ใน `POST /ariel/searches` ที่เลือก `sourceip, starttime, qid, sourceport` พร้อม subquery บน destinationip แนวทาง lab คือให้ผู้เรียนเขียน AQL กับตาราง DuckDB/SQLite ชื่อ `events` ที่คอลัมน์ชื่อเดียวกับ QRadar (`sourceip, destinationip, destinationport, username, qid, logsourceid, starttime` epoch ms, `payload`) ผ่าน translator บาง ๆ ที่แปลง `LAST n HOURS` → `starttime >= now()-n h`

## สิ่งที่ไม่มีอยู่จริงในที่สาธารณะ และวิธีชดเชย

การค้นคว้าทั้งสามสายยืนยันตรงกันว่าสิ่งต่อไปนี้ **ไม่มีใครเผยแพร่** และไม่ควรหลอกผู้เรียนว่ามี: (1) **QRadar offense export หรือ sample event/offense dataset จาก IBM** — ค้นทั้ง ibm.com และ GitHub พบแต่เอกสารวิธี export และ thread ปี 2019 ที่ไม่มีคำตอบ ([IBM Community thread](https://community.ibm.com/community/user/discussion/qradar-offense-dataset)) (2) **SOC ticket/case export จริงที่มี created/acknowledged/resolved + rule name + TP/FP disposition** — ใกล้สุดคือ UCI ServiceNow (ไม่มี rule/disposition) และ GUIDE (ไม่มี ack/resolve) (3) **LEEF corpus หรือชุด QRadar DSM sample events** — มีแต่บรรทัดตัวอย่างใน IBM docs, NXLog และ commit ของ Splunk Connect for Syslog (4) **ATT&CK label ระดับ event** — EVTX/OTRF/attack_data ติด label ระดับไฟล์หรือ dataset เท่านั้น (5) **MISP instance สาธารณะที่สมัครเองได้พร้อม API** — community ที่ MISP ลิสต์ล้วน vetted ยกเว้น SecureGRID และ ICS-CSIRT.io ([MISP communities](https://www.misp-project.org/communities/)) (6) **Cowrie dataset ที่มี label benign/malicious ต่อ session** และ **Zeek conn.log ที่มี beaconing label ต่อ connection** (7) **dataset ที่เป็น RFC 5424 structured syslog โดยกำเนิด** (8) **sample ของ NCSA real-SOC alert** ที่ paper บอกว่าปล่อย แต่ไม่พบ URL (9) **ตัวเลข MTTA/MTTR distribution จาก Expel/Red Canary** ที่ใช้ parameterize ได้

วิธีชดเชยที่ซื่อตรงที่สุดคือ **synthetic generator แบบ parameterized ที่ทุกพารามิเตอร์อ้างแหล่งสาธารณะได้**: ปริมาณและ funnel จาก Red Canary 2025 (419M → 8.5M → 110k ใน 1,700 องค์กร, 329B record/วัน) ([Red Canary](https://redcanary.com/threat-detection-report/methodology/)), สัดส่วน disposition จาก NCSA (0.01% / 49% / 27%) และ GUIDE (TP 19% / FP 35% / BP 46% ข้าม region), การกระจายเวลา resolve จาก UCI ServiceNow, ลำดับ attack phase จาก AIT-ADS `labels.csv`, rule name/level/falsepositives จาก Sigma จริง, และ shape ของ offense จาก `GET /siem/offenses` 23.0 สำหรับ LEEF ให้ถือว่าเป็น **target format ไม่ใช่ input** จึงไม่ต้องมี corpus — ใช้บรรทัดตัวอย่างของ IBM เป็น golden fixture ทำ round-trip test สำหรับ ATT&CK label ระดับ event ให้ใช้ Invoke-AtomicRedTeam execution logger (`Syslog-ExecutionLogger`, `WinEvent-ExecutionLogger`) บันทึกเวลาที่รัน atomic test เป็น ground truth เอง ([invoke-atomicredteam](https://github.com/redcanaryco/invoke-atomicredteam/tree/master/Public)) หรือใช้ PicoDomain red log ที่แม่น ±1 นาที สำหรับ MISP ให้ consume feed แบบไฟล์ (`manifest.json` + `<uuid>.json` จาก CIRCL/Botvrij) โดยไม่ต้องมี server และสำหรับ RFC 5424 ให้ผู้เรียน emit เองจาก BSD syslog ที่ parse ได้ ขั้นสุดท้ายของทุก lab คือ "นำโค้ดเดิมไปรันกับ export จริงของตัวเองใน NT cyfence" ซึ่งเป็นเหตุผลที่ schema ของ synthetic data ต้องยึด QRadar อย่างเคร่งครัด

## บทสรุป

ภาพที่เปลี่ยนไปจากสมมติฐานเดิมคือ "ของจริง" มีมากกว่าที่คิดในฝั่ง input (log ดิบ, alert จริงจาก Microsoft, rule corpus ที่ติด ATT&CK เกือบ 90%, feed ที่เรียกได้โดยไม่มี key) แต่ **ขาดสนิทในฝั่ง output ที่เป็น QRadar-native และฝั่ง lifecycle ของ SOC** ซึ่งเป็นสิ่งที่องค์กรไม่มีทางปล่อยสาธารณะ ข้อเท็จจริงนี้กลับเป็นข้อได้เปรียบของหลักสูตรสำหรับ NT cyfence: ผู้เรียนเป็นคนเดียวที่ถือ offense export และ ticket จริง ดังนั้นออกแบบทุก lab ให้ synthetic data ยึด schema ของ QRadar (LEEF 2.0, `GET /siem/offenses`, คอลัมน์ offense CSV ขั้นต่ำ) แล้วปิดท้ายด้วยการรันโค้ดเดิมกับข้อมูลจริงของตัวเอง — ตัวเลขที่ได้จะเป็น baseline ของ NT cyfence เองไม่ใช่ของ dataset

สองความเสี่ยงที่ต้องเฝ้าตั้งแต่วันแรกของการสอนคือ **license drift และ gating drift**: ภายในปีครึ่งที่ผ่านมา abuse.ch ปิด URL เก่าทั้งหมดเป็น 410, CIC-IDS2017 เพิ่มแบบฟอร์ม, SSLBL IP list ถูก deprecate และ GreyNoise จำกัด key กับ business email ขณะที่ Loghub กลับเปิดกว้างขึ้นเป็น CC-BY-4.0 บน Zenodo ทุก notebook จึงควร pin URL + checksum + วันที่ตรวจ (2026-11-02) และมี smoke test ที่ fail ดัง ๆ เมื่อ endpoint เปลี่ยน ส่วนบริบท QRadar เองก็เคลื่อน: SaaS หายไปแล้ว on-prem 7.5/7.6 ยังเป็น "current" แต่ไม่มีสัญญาระยะยาว ทักษะที่ lab ทั้งหกสร้าง (parse → normalise → dedupe/score → enrich → measure → detect แบบ vendor-neutral) จึงมีค่าในตัวเองไม่ว่าปลายทางจะเป็น QRadar, Cortex XSIAM หรืออื่นใด
