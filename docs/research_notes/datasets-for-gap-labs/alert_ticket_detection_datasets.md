## KQ1. Which public datasets contain SIEM-style alerts or offenses (for G2 alert overload: dedupe + risk-scoring)?

### Takeaway
Three datasets give real or realistic *alert streams with analyst dispositions* large enough to demonstrate dedupe/scoring reductions: Microsoft GUIDE (1.6M real alerts, TP/BP/FP labels, CDLA-Permissive-2.0), AIT-ADS (2.66M Wazuh/Suricata/AMiner alerts from a labelled testbed, CC BY 4.0, 96 MB) and SALAD (2.78M derived IDS alerts with triage/priority labels, CC BY 4.0). No public IBM QRadar offense export exists; BOTS and Sentinel sample data contain alert-type sourcetypes but are either Splunk-pre-indexed or tiny.

### Cited Findings

#### Microsoft GUIDE (Microsoft Security Incident Prediction)
- Maintainer: Microsoft; hosted at Kaggle — [Kaggle dataset](https://www.kaggle.com/datasets/Microsoft/microsoft-security-incident-prediction) (page resolves; JS-rendered, body not readable by fetch). Introduced in the paper "AI-Driven Guided Response for Security Operation Centers with Microsoft Copilot for Security" — [arXiv 2407.09017](https://arxiv.org/html/2407.09017v4).
- Size: over 13M evidence rows, 1.6M alerts, 1M incidents each with a ground-truth triage label; 26k alerts with remediation-action labels; 6.1k organizations; 9.1k unique DetectorIds; 33 entity types; 441 ATT&CK techniques; two-week window; "Region 2" telemetry — [arXiv 2407.09017](https://arxiv.org/html/2407.09017v4).
- Format: CSV, 70% train / 30% test, split stratified by triage grade, OrgId and DetectorId; benchmark set has 45 features plus labels and identifiers — [arXiv 2407.09017](https://arxiv.org/html/2407.09017v4).
- Columns include Id, OrgId, IncidentId, AlertId, Timestamp, DetectorId, AlertTitle, Category, MitreTechniques, IncidentGrade, ActionGrouped, ActionGranular, EntityType, EvidenceRole, DeviceId, DeviceName, Sha256, IpAddress, Url, AccountUpn, FileName, FolderPath, ThreatFamily, CountryCode — [arXiv 2407.09017](https://arxiv.org/html/2407.09017v4).
- Labels: IncidentGrade in {TP, BP (benign positive), FP}; Region 2 distribution approx. 14% TP / 34% FP / 52% BP; cross-region approx. 19% TP / 35% FP / 46% BP — [arXiv 2407.09017](https://arxiv.org/html/2407.09017v4).
- Real vs synthetic: real customer telemetry, pseudo-anonymized (SHA1 hashing then random IDs); noise added to timestamps — [arXiv 2407.09017](https://arxiv.org/html/2407.09017v4).
- License: CDLA-2.0 permissive per paper — [arXiv 2407.09017](https://arxiv.org/html/2407.09017v4); a 2026 survey also lists GUIDE as "CDLA 2.0" with a class distribution skewed to benign/FP — [arXiv 2605.08316](https://arxiv.org/pdf/2605.08316).
- Caveats stated by authors: BP has no standardized definition and ~81% of misclassifications involve BP; many BP/FP incidents come from third-party providers; single-region data; a table row listing 46k graded incidents is not reconciled with the 1M figure — [arXiv 2407.09017](https://arxiv.org/html/2407.09017v4).
- Extension: a 2026 paper says GUIDE lacks prioritization labels and released a per-organization queue-ranking label file on Kaggle — [arXiv 2607.16963](https://arxiv.org/pdf/2607.16963).

#### AIT Alert Data Set (AIT-ADS)
- Maintainer: Max Landauer, Florian Skopik, Markus Wurzenberger (AIT Austrian Institute of Technology); Zenodo DOI 10.5281/zenodo.8263181; published 2023-08-18, v1, modified 2024-10-14; license CC BY 4.0 — [Zenodo 8263181](https://zenodo.org/records/8263181).
- Files: `ait_ads.zip` 96.2 MB (alerts) + `labels.csv` 3.7 kB (start/end times of attack phases per scenario); alerts in JSON, one `_aminer.json` and one `_wazuh.json` (Wazuh + Suricata) per scenario — [Zenodo 8263181](https://zenodo.org/records/8263181).
- Size: 2,655,821 alerts (Wazuh 2,293,628; Suricata 306,635; AMiner 55,558) across 8 scenarios (fox 473,104; harrison 593,948; russellmitchell 45,544; santos 130,779; shaw 70,782; wardbeck 91,257; wheeler 616,161; wilson 634,246) — [Zenodo 8263181](https://zenodo.org/records/8263181).
- Provenance: lab-generated ("synthetic") — forensically generated by running three IDSs over the AIT Log Data Set V2 testbed logs (Zenodo 5789064) which contain 8 executions of a multi-step attack plus simulated normal user behaviour — [Zenodo 8263181](https://zenodo.org/records/8263181); companion paper "Introducing a New Alert Data Set for Multi-Step Attack Analysis", CSET '24 — [AIT publications](https://publications.ait.ac.at/en/publications/introducing-a-new-alert-data-set-for-multi-step-attack-analysis/).
- Labels: attack-phase time windows (scans, webshell upload, password cracking, privilege escalation, RCE, DNS exfiltration); a 2025 paper using it states label "-" marks false positives and most alerts are false positives — [arXiv 2509.12923](https://arxiv.org/pdf/2509.12923).
- Caveat: a 2026 risk-based-alerting paper reports much smaller per-IDS counts (Wazuh 23,116 alerts / 7,661 true; Suricata 9,186 / 44 true), evidently a subset or different counting — [arXiv 2609.02465](https://arxiv.org/pdf/2609.02465); treat Zenodo totals as authoritative.

#### SALAD: SOC Alert Labeled Analysis Dataset
- Maintainer: Nutthakorn Chalaemwongwan, KMITL (Thailand); Zenodo DOI 10.5281/zenodo.18912306; published 2026-03-08 v1; license CC BY 4.0 — [Zenodo 18912306](https://zenodo.org/records/18912306).
- Size/format: 2,778,424 alerts; CSV: `salad_train.csv` 644.6 MB, `salad_test.csv` 138.1 MB, `salad_val.csv` 138.1 MB, plus `datacard.md` and `stats.json`; 920.8 MB total — [Zenodo 18912306](https://zenodo.org/records/18912306).
- Provenance: derived from CIC-IDS2017 and UNSW-NB15 (lab network datasets), so lab-generated/derived, not real SOC alerts — [Zenodo 18912306](https://zenodo.org/records/18912306); [KMITL repository](https://dspace.kmitl.ac.th/handle/123456789/20648).
- Labels: ATT&CK mapping, triage decisions, priority scores, natural-language descriptions; 4 benchmark tasks with evaluation scripts; the Zenodo page does not state an explicit TP/FP field — [Zenodo 18912306](https://zenodo.org/records/18912306).

#### NCSA real-SOC alert study (sample only)
- "True Attacks, Attack Attempts, or Benign Triggers?" (USENIX Security 2024): 115M network alerts over 4 years (2018–2022), 24K–134K alerts/day, ~0.01% tied to true attacks, 49% benign triggers, 27% attack attempts; ground truth of 227 successful attacks over 20 years — [USENIX](https://www.usenix.org/conference/usenixsecurity24/presentation/yang-limin).
- Authors state they "release our code and a sample of the alert dataset", but the USENIX page lists no artifact link — [USENIX](https://www.usenix.org/conference/usenixsecurity24/presentation/yang-limin); [NSF PAR copy](https://par.nsf.gov//servlets/purl/10530815).

#### Splunk Boss of the SOC (BOTS) v1–v3
- Maintainer Splunk; GitHub licenses CC0-1.0 for all three repos; last pushes: botsv1 2024-08-08, botsv2 2022-11-01, botsv3 2020-06-18 — GitHub API via [splunk/botsv1](https://github.com/splunk/botsv1), [splunk/botsv2](https://github.com/splunk/botsv2), [splunk/botsv3](https://github.com/splunk/botsv3).

- BOTSv2: 16.4 GB full / 3.2 GB attack-only, "Pre-indexed Splunk" only (no JSON listed); sourcetypes include pan:threat, pan:traffic, ms:o365:management, osquery, mysql, auditd — [botsv2 README](https://raw.githubusercontent.com/splunk/botsv2/master/README.md).

#### Vendor aggregate numbers usable to parameterize a synthetic generator

- Expel 2026 Annual Threat Report analyses all 2025 incident data its SOC "collected, triaged, and resolved"; press coverage says identity-based attacks were more than two-thirds of incidents — [Expel blog](https://expel.com/blog/expels-2026-annual-threat-report-is-live/); [IT Brief](https://itbrief.com.au/story/identity-attacks-dominate-expel-s-2026-threat-report). ### Inferences
- Fit verdicts (G2 / G4 / G5):
  - **GUIDE** — G2 **Strong** (real alerts, repeated DetectorId+AlertTitle fingerprints across 6.1k orgs, TP/BP/FP labels let learners measure dedupe/scoring against ground truth); G4 **Partial** (has Timestamp + grade but no ack/resolve times; FP-rate-per-detector is computable); G5 **Partial** (MitreTechniques column lets learners build an "observed technique" Navigator layer; no rule logic).
  - **AIT-ADS** — G2 **Strong** (Wazuh/Suricata JSON, massive repetition of rule.id/signature_id, attack-phase windows give TP/FP ground truth; 96 MB fits a laptop); G4 **Weak** (no ticket lifecycle); G5 **Partial** (Suricata alerts can validate network Sigma rules; not host telemetry).
  - **SALAD** — G2 **Partial/Strong** (large CSV with triage + priority labels, but alerts derived from academic IDS datasets, so fingerprint realism is lower; ~1 GB CSV is pandas-friendly); G4 **Weak**; G5 **Partial** (ATT&CK-mapped alerts).
  - **BOTSv1 JSON-by-sourcetype** — G2 **Partial** (the `suricata`, `fgt_utm`, `nessus:scan` files give real-looking alert streams without labels; multi-GB); G4 **No**; G5 **Strong** as test telemetry for Windows/Sysmon Sigma rules (see KQ4). BOTSv2/v3 are Splunk-pre-indexed only, so **No** for pandas without a Splunk instance.
  - **Sentinel ASIM AlertEvent samples** — G2 **Weak** (dozens of rows) but **useful as a target schema** (SecondsToTriaged/SecondsToResolved fields map directly to MTTA/MTTR); G4 **Weak**; G5 **No**.
  - **CIC-IDS2017 / CTU-13 / MTA pcaps** — G2 **Partial** only if learners run Suricata/Zeek themselves to produce EVE alerts (adds a tooling step; CIC-IDS2017 PCAPs are ~51 GB); G4 **No**; G5 **Partial** for network Sigma rules.
  - **QRadar offense CSV** — the only QRadar-native format is learners' own export; for the lab, map GUIDE/AIT-ADS columns onto QRadar offense-like fields (rule name ↔ DetectorId/AlertTitle, magnitude ↔ composite score) so the dedupe/scoring code later runs unchanged on a real offense export.
- The Red Canary funnel (419M → 8.5M → 110k) and NCSA ratios (0.01% true attacks, 49% benign triggers, 27% attack attempts) are defensible parameters for a synthetic "QRadar offense" generator when a real export cannot be shared.

### Gaps
- GUIDE's on-disk size (MB) and Kaggle-listed license string could not be read (JS page); confirm by `kaggle datasets metadata Microsoft/microsoft-security-incident-prediction`.
- AIT-ADS: the exact mechanism for marking false positives inside `labels.csv` is not described on Zenodo; verify after download.
- SALAD: datacard not fetched; existence of an explicit TP/FP column unconfirmed.
- NCSA sample dataset: no public URL located.
- No public QRadar offense export, LEEF alert sample set, or QRadar sample offense CSV was found anywhere.
- Expel quantitative SOC metrics (alert volumes, FP %) were not extractable; the report pages are gated/JS.

## KQ2. Which public incident/ticket datasets with timestamps exist (for G4 SOC metrics: MTTD/MTTA/MTTR, FP rate per rule, weekly reports)?

### Takeaway
Real SOC case exports are effectively not public. The best lifecycle-timestamp dataset is the UCI "Incident management process enriched event log" (ServiceNow, 24,918 IT incidents, opened/created/resolved/closed timestamps, priority, SLA flag, CC BY 4.0) — it is an IT service desk, not a SOC, and has no rule name or TP/FP disposition. VCDB (10,596 breach incidents, CC BY-SA 4.0) carries timeline *durations* (compromise/discovery/containment in days/hours), not timestamps. GUIDE supplies disposition per alert/incident but no ack/resolve times.

### Cited Findings

#### UCI Incident management process enriched event log (ServiceNow)
- Creators Claudio Amaral, Marcelo Fantinato, Sarajane Peres (Univ. of São Paulo); donated 2019-07-13; DOI 10.24432/C57S4H; license CC BY 4.0 — [UCI dataset 498](https://archive.ics.uci.edu/dataset/498/incident+management+process+enriched+event+log).
- 141,712 events over 24,918 incidents; 36 attributes (1 case id, 1 state id, 32 descriptive, 2 dependent variables); CSV `incident_event_log.csv` 44.1 MB, zip 2.3 MB (zip URL returned HTTP 200 on 2026-11-02) — [UCI dataset 498](https://archive.ics.uci.edu/dataset/498/incident+management+process+enriched+event+log).
- Attributes: `opened_at`, `sys_created_at`, `resolved_at`, `closed_at`, `priority` (from impact × urgency), `impact`/`urgency` (1 High–3 Low), `category`, `assignment_group`, `incident_state` (8 levels), `reassignment_count`, `made_sla` (boolean) — [UCI dataset 498](https://archive.ics.uci.edu/dataset/498/incident+management+process+enriched+event+log).
- Provenance: real, anonymized audit data from a ServiceNow instance at an IT company; time period not stated — [UCI dataset 498](https://archive.ics.uci.edu/dataset/498/incident+management+process+enriched+event+log). A Kaggle mirror exists ("vipulshinde incident response log") — [Baselight mirror listing](https://baselight.app/u/kaggle/dataset/vipulshinde_incident_response_log).

#### VERIS Community Database (VCDB)
- Maintainer Verizon RISK / vz-risk; license Creative Commons Attribution-ShareAlike 4.0 (LICENSE.txt); last push 2026-10-12 — [vz-risk/VCDB](https://github.com/vz-risk/VCDB); [LICENSE.txt](https://raw.githubusercontent.com/vz-risk/VCDB/master/LICENSE.txt).
- Formats: per-incident JSON under `data/json/` (submitted/validated pipeline) and `data/csv/vcdb.csv.zip` (15.1 MB zip); the CSV unzips to 172 MB with 10,596 incident rows × 2,683 one-hot columns (measured locally 2026-11-02 from the downloaded zip) — [data/csv](https://github.com/vz-risk/VCDB/tree/master/data/csv).
- Timeline fields are durations with unit flags, e.g. `timeline.compromise.value` + `timeline.compromise.unit.{Seconds,Minutes,Hours,Days,Weeks,Months,Years,Never,Unknown,NA}`, `timeline.containment.*`, and `plus.timeline.notification.{day,month,year}` (measured from the CSV header) — [vcdb.csv.zip](https://github.com/vz-risk/VCDB/raw/master/data/csv/vcdb.csv.zip).
- The CSV deliberately excludes one source folder "as they would unwittingly bias the dataset" — [data/csv/NOTE.txt](https://raw.githubusercontent.com/vz-risk/VCDB/master/data/csv/NOTE.txt).
- Provenance: real, publicly disclosed breaches coded to the VERIS schema; the README says no unrestricted comprehensive raw incident dataset otherwise exists — [VCDB README](https://raw.githubusercontent.com/vz-risk/VCDB/master/README.md).

#### GUIDE (as an incident dataset)
- 1M incidents with triage grade (TP/BP/FP), 26k alerts with remediation-action labels, `Timestamp` (noised), `DetectorId`, `AlertTitle`, `Category`, `OrgId`, two-week span — [arXiv 2407.09017](https://arxiv.org/html/2407.09017v4).

- QRadar offenses export to CSV/XML with user-chosen columns — [IBM Docs: Exporting offenses](https://www.ibm.com/docs/en/SSKMKU/com.ibm.qradar.doc/t_qradar_export_off.html). ### Inferences
- Fit verdicts (G2 / G4 / G5):
  - **UCI ServiceNow event log** — G4 **Strong for the mechanics** (opened→resolved→closed timestamps, priority, SLA flag, reassignment count let learners compute MTTA-like and MTTR, weekly rollups, SLA breach %); **Partial for realism** (no rule name, no TP/FP disposition — learners must join or synthesize a `rule_name`/`disposition` column); G2 **No**; G5 **No**.
  - **VCDB** — G4 **Partial** (compute discovery/containment duration distributions by industry/action as benchmark context; no per-ticket timestamps, so no MTTA); G2 **No**; G5 **Weak** (VERIS actions ≠ ATT&CK, though mappings exist).
  - **GUIDE** — G4 **Partial** (FP rate per DetectorId and incident volume per org per day are directly computable; MTTA/MTTR impossible because no ack/resolve timestamps).
  - **Sentinel ASIM AlertEvent** — G4 **Schema reference only**: its `SecondsToTriaged`/`SecondsToResolved` fields are a ready-made target shape for a QRadar offense → metrics pipeline.
- Honest framing for learners: no real SOC case export with created/acknowledged/resolved + rule + disposition is public. A defensible lab design is a synthetic offense/ticket generator whose parameters come from public numbers (Red Canary funnel 419M→8.5M→110k, NCSA 0.01% true / 49% benign / 27% attempts, GUIDE 19/35/46 TP/FP/BP split) with the UCI log supplying realistic lifecycle-time distributions, then validating the metrics code against a learner's own QRadar offense CSV.
- QRadar offense CSV columns are user-selected at export; the lab should standardize a minimal column list (ID, Description, Offense Source, Magnitude, Severity, Start Time, Last Updated, Assigned To, Status, Closing Reason) so pandas code is portable.

### Gaps
- No public dataset found containing security tickets/cases with created, acknowledged and resolved timestamps plus rule name and TP/FP disposition.
- UCI dataset time period not stated on the page.
- QRadar REST `/siem/offenses` field list (start_time, last_updated_time, close_time in epoch-ms, magnitude, severity, credibility, relevance, closing_reason_id, etc.) could not be verified by fetch in this session (the IBM doc URL tried returned an index page); verify against the learners' QRadar API docs (`/api_doc`) before building the schema.
- Expel/Red Canary do not publish MTTA/MTTR distributions suitable for direct parameterization (Red Canary methodology page has no MTTR figure).

## KQ3. Sigma corpus size, license, ATT&CK coverage, and pySigma backends for QRadar/Splunk/Elastic; Elastic and Splunk rule corpora as alternatives (G5)

### Takeaway
SigmaHQ/sigma currently holds 3,161 production rules in `rules/` (2,425 Windows) plus 474 emerging-threat and 141 threat-hunting rules, licensed under DRL 1.1; 2,817 of 3,161 `rules/` carry a technique-level ATT&CK tag spanning 391 distinct technique/sub-technique IDs. IBM maintains a stable pySigma QRadar AQL backend (`ibm-qradar-aql`, MIT, last commit 2026-10-29); official Splunk and Elasticsearch backends were released in Oct/Aug 2026. Elastic detection-rules (2,318 TOML rules, Elastic License 2.0) and Splunk security_content (~2,190 YAML detections, Apache-2.0) are the vendor-side alternatives with risk_score/ATT&CK metadata.

### Cited Findings

## KQ5. Which tools compute ATT&CK coverage from rule metadata, and what input formats do they expect?

### Takeaway
Four maintained open-source paths exist: `sigma analyze attack` (reads a Sigma rule directory, writes a Navigator layer v4.4 heatmap), DeTT&CT v2.2.0 (GPL-3.0; reads its own `techniques-administration` YAML v1.2 with detection scores −1..5 / visibility 1..4 and emits Navigator layers + Excel), mitreattack-python `navlayers` (Apache-2.0; load/validate/merge layers, export Excel/SVG) and the ATT&CK Navigator web app itself (Apache-2.0, app v5.3.2, layer spec up to v4.5). Elastic detection-rules has its own navigator.py for its TOML corpus.

### Cited Findings
- **sigma-cli `analyze attack`**: Click command "Create MITRE ATT&CK heatmaps from Sigma rule set", score functions selectable, options for file-name pattern, `--min-level`, `--min-status`, max/zero colors, fixed max score, min score; output JSON layer with `"navigator": "4.8.1"`, `"layer": "4.4"`; also `analyze logsource` (stats) and a field-extraction command for a target backend/pipeline — [sigma-cli analyze.py](https://github.com/SigmaHQ/sigma-cli/blob/main/sigma/cli/analyze.py). Example output in the Sigma repo: `other/sigma_attack_nav_coverage.json` (ATT&CK 19.1, gradient 0–20, per-technique `score`, `tactic`) — [sigma_attack_nav_coverage.json](https://github.com/SigmaHQ/sigma/blob/master/other/sigma_attack_nav_coverage.json).
- **DeTT&CT** (rabobank-cdc/DeTTECT): GPL-3.0; pushed 2026-10-19; 2,355 stars; latest version 2.2.0; scores data-source quality, visibility coverage, detection coverage and threat-actor behaviour for Enterprise/ICS/Mobile; visualised via Navigator layer JSON; Excel export; the third-party Dettectinator has plugins to read detections from a SIEM/EDR into the DeTT&CT YAML — [DeTTECT README](https://github.com/rabobank-cdc/DeTTECT/blob/master/README.md); GitHub API.
- DeTT&CT techniques-administration YAML: keys `version` (1.2), `file_type: techniques-administration`, `name`, `domain` (enterprise-attack/ics-attack/mobile-attack), `platform`, `techniques[]` each with `technique_id`, optional `technique_name`, `detection{applicable_to, location (prefix e.g. "SIEM: Rule A"), comment, score_logbook[{date, score, comment}]}` and `visibility{…}`; detection score range −1..5, visibility 1..4; `-cd/--count-detections` uses location prefixes — [DeTT&CT wiki: YAML administration techniques](https://github.com/rabobank-cdc/DeTTECT/wiki/YAML-administration-techniques).
- **ATT&CK Navigator** (mitre-attack/attack-navigator): Apache-2.0; pushed 2026-11-01; layer format specs v1.0 through v4.5 under `layers/spec/`; app version 5.3.2 (`nav-app/package.json`) — [attack-navigator layers/spec](https://github.com/mitre-attack/attack-navigator/tree/master/layers/spec); GitHub API.
- **mitreattack-python** (`mitreattack.navlayers`): Apache-2.0; pushed 2026-10-13; core modules load/validate/manipulate/save layers adhering to layer format 4.3 while accepting v3.0 and 4.x (upgrading them); `layerops` merges layers; exporters `to_excel`, `to_svg`; also modules `attackToExcel`, `stix20`, `diffStix`, `download_stix` — [navlayers README](https://github.com/mitre-attack/mitreattack-python/blob/main/mitreattack/navlayers/README.md); GitHub API.
- **Elastic detection-rules**: `detection_rules/navigator.py` and `detection_rules/attack.py` generate layers from rule `threat` mappings on every successful build; bundled ATT&CK STIX v18.1.0/v19.1 and a v18→v19 technique redirect map; published gist layers (full and per-platform) — [ATT&CK-coverage.md](https://github.com/elastic/detection-rules/blob/main/docs-dev/ATT%26CK-coverage.md); tree listing via GitHub API.
- **Splunk security_content**: each detection YAML has `mitre_attack_id` (list) — [example detection](https://raw.githubusercontent.com/splunk/security_content/develop/detections/endpoint/7zip_commandline_to_smb_share_path.yml).

### Inferences
- Input-format map for the G5 lab:
  - Sigma YAML directory → `sigma analyze attack count <rules_dir> layer.json` → Navigator layer 4.4 (counts rules per technique; filter `--min-status stable` to get a "deployed" view).
  - Sigma → QRadar conversion results (success/failed per rule) → write a DeTT&CT `techniques-administration` YAML where `detection.location` = "QRadar: <rule title>" and `score` reflects conversion success + logsource availability → `dettect.py d … -l` style layer (exact CLI flags not verified here; see wiki pages "dettect.py - help texts").
  - Any two layers (e.g., Sigma-corpus coverage vs. QRadar-converted coverage vs. OTRF telemetry-validated coverage) → `mitreattack.navlayers.manipulators.layerops` to produce a difference/overlap layer → `to_svg`/`to_excel` for the report.
- Layer-version skew is manageable: sigma-cli writes 4.4, mitreattack-python targets 4.3 but accepts 4.x, and Navigator 5.3.2 reads up to 4.5.
- Coverage computed from tags alone is an upper bound; DeTT&CT's data-source/visibility scoring is the right place to encode "QRadar is not ingesting Sysmon", which is the typical cause of overstated coverage.

### Gaps
- DeTT&CT exact CLI invocation for layer generation (`-l`) and the installation page were not fetched (wiki index only); confirm from `dettect.py -h`.
- Whether `sigma analyze attack` ATT&CK version (19.1 in the shipped layer) matches the learners' Navigator instance was not checked.
- pySigma QRadar backend does not report an ATT&CK coverage view of *unconvertible* rules; learners must log conversion exceptions themselves.
