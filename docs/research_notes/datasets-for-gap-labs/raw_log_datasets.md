# Public raw log datasets for SOC training labs (gaps G1 and G6)

Research date: 2026-11-02. All URLs below were resolved on that date unless a finding says otherwise (secrepo.com, GitHub and Zenodo were fetched via `curl`/REST APIs; Zenodo sizes come from the Zenodo records API; GitHub "pushed" dates come from the GitHub REST API). Sizes are as published by the maintainer; "MB" from Zenodo API are decimal megabytes.

Legend for fit verdicts: G1 = raw multi-format logs to parse with Python and re-emit as LEEF / ECS / OCSF. G6 = labelled anomalies / ground truth to score rule-based vs. ML detection with precision/recall.

## Q1. Which Loghub (LogPAI) datasets fit, which carry anomaly labels, and what are the current download terms and sizes?

### Takeaway
Loghub is fully open as of 2026: all 19 raw datasets are on Zenodo record 8196385 (published 2023-07-31, record metadata updated 2024-01-28) under CC-BY-4.0, with no request form, while the GitHub LICENSE file still restricts use to "research or academic work" with citation. Only HDFS_v1, HDFS_v3 (TraceBench), Hadoop, OpenStack, BGL and Thunderbird carry anomaly/alert labels; the Windows dataset is a CBS.log (not EVTX), and Apache is an error log (not an access log).

Label and provenance details
- HDFS_v1 "is generated in a private cloud environment using benchmark workloads, and manually labeled through handcrafted rules to identify the anomalies. The logs are sliced into traces according to block ids. Then each trace associated with a specific block id is assigned a groundtruth label: normal/anomaly." Preprocessed files: HDFS_templates.csv, anomaly_label.csv, Event_traces.csv, Event_occurrence_matrix.csv, HDFS.npz. Origin: Xu et al., SOSP 2009. — [loghub/HDFS README](https://github.com/logpai/loghub/tree/master/HDFS)
- HDFS_v2 is "provided as-is without further modification or labelling, which may involve both normal and abnormal cases"; three nodes' logs were lost. — [loghub/HDFS README](https://github.com/logpai/loghub/tree/master/HDFS)
- HDFS_v3 TraceBench: 17 injected faults, >180 h, 364 files, >370,000 traces, provided as normal_trace.csv / failure_trace.csv. — [loghub/HDFS README](https://github.com/logpai/loghub/tree/master/HDFS)
- BGL: LLNL BlueGene/L, 131,072 processors; "In the first column of the log, '-' indicates non-alert messages while others are alert messages." Source: USENIX CFDR, Oliner & Stearley DSN 2007. — [loghub/BGL README](https://github.com/logpai/loghub/tree/master/BGL)
- Thunderbird: Sandia, 9,024 processors; same "-" = non-alert labelling convention. — [loghub/Thunderbird README](https://github.com/logpai/loghub/tree/master/Thunderbird)
- Hadoop: 5-machine lab cluster running WordCount and PageRank with injected failures (machine down, network disconnection, disk full); labels in `abnormal_label.txt` (per job ID). README table flags "Check #56" next to the label mark. — [loghub/Hadoop README](https://github.com/logpai/loghub/tree/master/Hadoop); [loghub README](https://github.com/logpai/loghub)
- OpenStack: generated on CloudLab; "Both normal logs and abonormal cases with failure injection are provided"; usage example points to a DeepLog preprocessing script. — [loghub/OpenStack README](https://github.com/logpai/loghub/tree/master/OpenStack)
- Windows: "collected by aggregating a number of logs from a lab computer running Windows 7. The original logs were located at `C:\Windows\Logs\CBS`" (Component Based Servicing), >27 GB, 226+ days. — [loghub/Windows README](https://github.com/logpai/loghub/tree/master/Windows)
- Linux: "/var/log/messages on a Linux server over a period of 260+ days, as part of the Public Security Log Sharing Site project" (log-sharing.dreamhosters.com). — [loghub/Linux README](https://github.com/logpai/loghub/tree/master/Linux)
- Apache: "We provide an error log for the purpose of research on anomaly detection and diagnosis", also from the Public Security Log Sharing Site. — [loghub/Apache README](https://github.com/logpai/loghub/tree/master/Apache)
- OpenSSH: "collected the log from an OpenSSH server in our lab over a period of 28+ days." — [loghub/OpenSSH README](https://github.com/logpai/loghub/tree/master/OpenSSH)
- Mac: "/var/log/system.log on a Macbook after 7 days of use." — [loghub/Mac README](https://github.com/logpai/loghub/tree/master/Mac)

### Inferences
- License conflict to disclose to learners: Zenodo publishes the files under CC-BY-4.0, while the GitHub LICENSE narrows use to "research or academic work". A training lab is arguably academic, but a commercial training vendor should rely on the Zenodo CC-BY-4.0 copy and keep the citation notice.
- G1 verdicts: Linux (BSD-syslog `/var/log/messages`, 2.25 MiB, 2006-era), OpenSSH (70 MiB, auth failures), Mac (system.log), Apache error log, Zookeeper, Proxifier are small, real, unnormalised text logs ideal for "no parser" exercises and LEEF/ECS re-emission. Windows (CBS.log) does NOT satisfy an "EVTX" requirement; Apache is an error log, so it does not satisfy "combined access log".
- G6 verdicts: HDFS_v1 (block-level labels), BGL and Thunderbird (per-line alert tags), Hadoop (job-level labels, caveat issue #56), OpenStack (failure-injection sessions) are the only Loghub sets with ground truth, and they are what loglizer/DeepLog benchmarks use. Loghub-2k structured CSVs and Loghub-2.0 give template ground truth to score Drain3 parsing accuracy (not anomaly detection). OpenSSH/Linux have no labels; learners would have to self-label brute-force bursts (defensible for a rules-vs-ML exercise but not "vendor ground truth").
- Tooling age: loglizer's code is 2019-era but its only dependencies are scikit-learn and pandas, so it runs under Python 3 with minor fixes; Drain3 and logparser are maintained (2025 pushes). deep-loglizer provides DeepLog implementations but is unmaintained since 2023.

### Gaps
- Loghub's README gives no explicit "last updated" date; the Zenodo record's `updated` field (2024-01-28) is the best proxy.
- The nature of Hadoop issue #56 (label quality) was not read; treat Hadoop labels as "flagged by maintainers".
- Whether loglizer's current master runs cleanly under Python 3.12 was not tested.

## Q2. Which public Windows EVTX collections exist, and do they carry ATT&CK labels?

### Takeaway
Three complementary EVTX corpora exist with ATT&CK mapping: sbousseaden/EVTX-ATTACK-SAMPLES (~200 EVTX, GPL-3.0, last push Jan 2023), mdecrevoisier/EVTX-to-MITRE-Attack (>270 EVTX, CC0-1.0, last push May 2026), and OTRF Security-Datasets (JSON, not EVTX; MIT per repo metadata, last push Mar 2024). Yamato-Security's sample repo aggregates the first two plus DeepBlueCLI but has no license file; python-evtx ships small real EVTX test files under Apache-2.0.

### Inferences
- G1 verdicts: sbousseaden and mdecrevoisier give genuine binary EVTX that learners must parse (python-evtx or evtx_dump) before normalising; this is the most realistic "SIEM has no parser" exercise for Windows. OTRF/Mordor is already JSON (Winlogbeat-style), so it is a lighter G1 exercise (field renaming to ECS/OCSF rather than binary parsing). Splunk attack_data provides Windows Security/Sysmon in text/JSON mapped to techniques. All are lab-generated attack simulations, not production data.
- G6 verdicts: ATT&CK technique labels are at file/dataset granularity (each file = one technique), not per-event, so precision/recall can be computed only at the "did the detector flag this file/session" level, or learners must hand-label events inside each file. BOTSv1 provides a large mixed haystack (benign + attack) suitable for threshold-vs-ML comparison but with ground truth encoded as CTF answers rather than per-event labels. LANL Unified Host is the only large real-production Windows host log corpus, but it has no red-team labels (its 2015 sibling cyber1 does, for auth events only).
- Licensing: GPL-3.0 (sbousseaden, DeepBlueCLI, PicoDomain) only matters if redistributing the samples; CC0 (mdecrevoisier, BOTS) and Apache-2.0 (attack_data, python-evtx) are the simplest for course packs. Yamato's repo has no license, so redistribute from the upstream repos instead.

### Gaps
- Exact EVTX file counts per repository were not enumerated (README claims "200" and ">270").
- Security-Datasets license ambiguity (MIT vs GPL-3.0 text in README) was not resolved by the maintainers' pages fetched.
- "DFIR challenge" EVTX sets (CyberDefenders, Blue Team Labs) were not surveyed; they generally sit behind logins.

## Q3. Which web/access-log datasets are real, and which contain attacks?

### Takeaway
Genuinely real production access logs that are freely redistributable are: the 1995 Internet Traffic Archive traces (NASA, EPA, ClarkNet, Saskatchewan, Calgary), SecRepo's own daily nginx-style `access.log` files (2015 to Oct 2026, CC BY 4.0), the Harvard Dataverse "Online Shopping Store" nginx log (CC0, 274 MB zip, 2018) and the 2026 Zenodo "Web Server Log Dataset" from two Indonesian public bodies (MIT, with YAML attack-labelling rules). Attack-labelled HTTP corpora (CSIC 2010, ECML/PKDD 2007, AIT-LDS, SR-BH 2020) are lab-generated or honeypot-style rather than production.

### Cited Findings

Internet Traffic Archive (ITA) 1995 traces
- NASA-HTTP: two traces of all HTTP requests to the NASA Kennedy Space Center WWW server, July 1–31 and August 1995 (server down 01/Aug 14:52:01 to 03/Aug 04:36:13 for Hurricane Erin); 3,461,612 requests total; July 20.7 MB gz / 205.2 MB uncompressed, August 21.8 MB gz / 167.8 MB; ASCII one line per request with host, timestamp (-0400), quoted request, reply code, bytes; "The traces may be freely redistributed"; hosts and requests fully preserved, "please do not however attempt any analysis beyond general traffic patterns". — [NASA-HTTP](https://ita.ee.lbl.gov/html/contrib/NASA-HTTP.html)
- Calgary-HTTP: Oct 24 1994 to Oct 11 1995 (353 days), 726,739 requests; requesting hosts replaced by "local"/"remote" and paths replaced by `num.type` identifiers (anonymised). — [Calgary-HTTP](https://ita.ee.lbl.gov/html/contrib/Calgary-HTTP.html)
- EPA-HTTP: 24 h from 23:53:25 EDT Aug 29 1995; 47,748 requests (46,014 GET, 1,622 POST, 107 HEAD, 6 invalid); 1.1 MB compressed / 4.4 MB; date field is `[DD:HH:MM:SS]` (non-standard); "may be freely redistributed". — [EPA-HTTP](https://ita.ee.lbl.gov/html/contrib/EPA-HTTP.html)
- ClarkNet-HTTP: Aug 28–Sep 10 1995, 3,328,587 requests; Saskatchewan-HTTP: Jun 1–Dec 31 1995, 2,408,625 requests; both preserve originating hosts. — [ClarkNet-HTTP](https://ita.ee.lbl.gov/html/contrib/ClarkNet-HTTP.html); [Sask-HTTP](https://ita.ee.lbl.gov/html/contrib/Sask-HTTP.html)
- The ITA traces index lists Calgary, ClarkNet, EPA, NASA, Saskatchewan, SDSC and WorldCup98 (~1.3 billion requests) server logs. — [ITA traces](https://ita.ee.lbl.gov/html/traces.html)
- A Kaggle re-host "NASA HTTP Logs Dataset - Processed For LSTM Models" is pre-aggregated to per-minute counts (not raw lines); provenance is the ITA record. — [Baselight index of Kaggle dataset](https://baselight.app/u/kaggle/dataset/pasanbhanuguruge_nasa_http_logs_processed_for_lstm_models)

- SecRepo "Web Logs from Security Repo": "these logs are generated by you the community, and me updating this site"; directory `/self.logs/` contains yearly folders 2015/ and 2016/ plus daily `access.log.YYYY-MM-DD[.gz]` and `error.log.YYYY-MM-DD[.gz]` files through at least `error.log.2026-10-29.gz` (daily sizes in the tens of KB, e.g. 17–94 KB in Jan 2017). Site licence: "All data generated and hosted by Security Repo is done so under the following license (exceptions noted where applicable). Zenodo 20001206 adds real logs with real attacks plus auth.log/syslog from the same hosts (multi-format correlation) but is three months old at time of writing and its labelling is rule-derived.
- G6 verdicts: SR-BH 2020 and CSIC 2010 provide per-request labels and are the classic rules-vs-ML web attack benchmarks (CSIC is synthetic; SR-BH is honeypot-style real traffic with WAF-derived labels). The Indonesian dataset's YAML rules are themselves regex-style rules, so comparing ML against them risks circularity; it is better used as a G1 corpus with weak labels.
- The NASA and ClarkNet logs lack labelled attacks; any anomaly exercise on them must be unsupervised (e.g. request-rate spikes).

## Q4. Which Linux auth/syslog/honeypot datasets exist?

### Takeaway
Real honeypot JSON is available from SecRepo (Amun + Glastopf, ~994k entries, CC BY 4.0) and the CyberLab honeynet (Cowrie 1.6.0/2.0.2 on ~50 nodes, May 2019–Feb 2020, CC-BY-4.0, daily JSON on Zenodo). Real Linux auth logs come from SecRepo `auth.log.gz` (~86k lines, mostly failed SSH), Loghub Linux/OpenSSH, and the 2004–2006 Chuvakin bundles; the only large real auth corpus with red-team ground truth is LANL's 2015 "Comprehensive, Multi-Source Cyber-Security Events" (CC0, email-gated). DShield/ISC publishes aggregated API data (CC BY-NC-SA 4.0), not raw honeypot dumps.

### Cited Findings
- SecRepo `auth.log`: "approx 86k lines, and mostly failed SSH login attempts" at `https://secrepo.com/auth.log/auth.log.gz`; `honeypot.json.zip`: "Data from various honeypots (Amun and Glastopf) used for various BSides presentations… Approx 994k entries, JSON format"; Squid access log "combined from several sources (24MB compressed, ~200MB uncompresed)"; manifest `license` field is null for these self-hosted files, so the site-wide CC BY 4.0 applies; all returned HTTP 200 on 2026-06-06 per the manifest. — [secrepo site-links.json](https://www.secrepo.com/data/site-links.json); [secrepo.com licence statement](https://www.secrepo.com/)
- SecRepo also links third-party honeypot sets: "Honeypot Data with GeoIP info" (`marx-geo.tar.gz`, DDS blog, licence Unknown) and `marx.tar.gz`; "Threat Research Private – Encrypted data collected from SSH honeypots". — [secrepo site-links.json](https://www.secrepo.com/data/site-links.json)
- CyberLab honeynet dataset (Zenodo 3687527, CC-BY-4.0, published 2020-02-29): "all data collected by the CyberLab honeynet experiment, from May 2019 to February 2020… Cowrie honeypot… versions 1.6.0 and 2.0.2… deployed on approximately 50 nodes at different EU and US universities and companies… All public IP addresses in the dataset are pseudonymized"; one `cyberlab_YYYY-MM-DD.json.gz` per day (2019-05-13 to 2020-02-29), per-file sizes from 1.6 MB (May 2019) to 122.5 MB (2019-12-08); high-interaction sessions after 2019-11-08 tagged `sensor:ubuntu_basic_pool`; geolocation added. — [Zenodo 3687527](https://zenodo.org/records/3687527)

- SANS ISC/DShield: API data is "licensed under a Creative Commons Attribution-NonCommercial-ShareAlike 4.0 International (CC BY-NC-SA 4.0) License"; "Do not resell the data… Currently, we do not require authentication (we may in the future)"; `webhoneypotsummary` endpoint gives daily summaries, bulk feeds give daily summaries. — [isc.sans.edu/api](https://isc.sans.edu/api/)
- ISC diaries on DShield sensors: raw `cowrie.json*` files on a sensor are retained only 7 days; web honeypot logs at `/srv/db/webhoneypot.json`; data is per-sensor, viewable in the user portal. — [ISC diary 30024](https://isc.sans.edu/diary/30024); [ISC diary 29412](https://isc.sans.edu/diary/29412)
- LANL "Comprehensive, Multi-Source Cyber-Security Events" (2015, CC0): 58 consecutive days, 1,648,275,307 events, 12,425 users, 17,684 computers; files auth.txt.gz 7.2 GB, proc.txt.gz 2.2 GB, flows.txt.gz 1.1 GB, dns.txt.gz 177 MB, redteam.txt.gz 4.8 KB; auth fields: time, source user@domain, destination user@domain, source computer, destination computer, authentication type, logon type, authentication orientation, success/failure; de-identified with time starting at epoch 1; "Downloads require an email address and a description of intended use"; citation Kent 2015, DOI 10.17021/1179829. — [LANL cyber1](https://csr.lanl.gov/data/cyber1/)
- Loghub Linux (/var/log/messages, 25,567 lines, 263.9 days, from the Public Security Log Sharing Site) and OpenSSH (655,146 lines, 28.4 days, lab server) — see Q1. — [loghub README](https://github.com/logpai/loghub)
- Chuvakin bundles include `/var/log/secure` and `/var/log/messages` from 2005–2006 RedHat/Fedora systems with a brute-force compromise in Bundle 4 — see Q3. — [log-sharing.dreamhosters.com](http://log-sharing.dreamhosters.com/)
- AIT-LDS v2.0 includes "authentication logs… audit logs… syslog" with per-line attack labels — see Q3. — [Zenodo 5789064](https://zenodo.org/records/5789064)

### Inferences
- G1 verdicts: SecRepo auth.log and Loghub Linux/OpenSSH are BSD-style syslog (RFC 3164 timestamps), good for parsing into ECS `event.outcome`/`source.ip`/`user.name` and LEEF `usrName`/`src`. CyberLab and SecRepo honeypot JSON are nested JSON with per-event schemas (Cowrie `eventid` such as `cowrie.login.failed`), a good "JSON with no DSM" exercise. No dataset found is natively RFC 5424 structured syslog; learners will have to emit 5424 themselves.
- G6 verdicts: honeypot data is 100% hostile by construction, so "anomaly" labels are trivial; it suits template mining (Drain3) and clustering rather than precision/recall. LANL cyber1 is the only real, large auth corpus with explicit red-team ground truth (redteam.txt), and is the canonical DeepLog/graph-anomaly benchmark, but is 7.2 GB compressed and email-gated. AIT-LDS gives labelled auth/syslog but is synthetic and non-commercial.
- DShield is not usable as a redistributable raw dataset; it is an API/feed under CC BY-NC-SA.

### Gaps
- Total size of the CyberLab dataset was not summed (roughly 280 daily files; several GB).
- The SecRepo HEAD requests returned no Content-Length, so exact byte sizes of auth.log.gz and honeypot.json.zip are unverified beyond the manifest text.
- No public Cowrie dataset with per-session benign/malicious labels was found (all are attack-only).

## Q5. Are there official or public LEEF and CEF sample files learners can use as output targets?

### Takeaway
IBM's LEEF Format Guide publishes exact example header and attribute lines (LEEF 1.0 and 2.0, with RFC 3164/5424 syslog prefixes) and the OpenText/ArcSight CEF Implementation Standard PDF contains the canonical `CEF:0|Security|threatmanager|1.0|100|worm successfully stopped|10|…` example; however, no public corpus of LEEF or QRadar DSM sample event files was found. ECS (v9.5.0, Apache-2.0 repo) and OCSF (schema 1.9.0, Apache-2.0 repo) are the open alternatives.

### Cited Findings
- IBM LEEF event components page gives verbatim examples: syslog headers `<13>Jan 18 11:07:53 192.168.1.1` (RFC 3164) and `<13>1 2019-01-18T11:07:53.520Z 192.168.1.1`, `<133>1 2019-01-18T11:07:53.520+07:00 myhostname` (RFC 5424); LEEF headers `LEEF:1.0|Microsoft|MSExchange|4.0 SP1|15345|`, `LEEF:2.0|Lancope|StealthWatch|1.0|41|^|`, `LEEF:2.0|Vendor|Product|Version|EventID|x5E|`, `LEEF:1.0|Microsoft|MSExchange|2007|Logon Failure|`; attributes `src=192.0.2.0 dst=172.50.123.1 sev=5 cat=anomaly srcPort=81 dstPort=21 usrName=joe.black`; attributes separated by tab or (LEEF 2.0) a declared delimiter given as a character or hex `0x`/`x` + 1–4 hex digits; EventID ≤255 chars; "QRadar cannot route IPv6 addresses" in the syslog header. — [IBM LEEF event components](https://www.ibm.com/docs/en/dsm?topic=overview-leef-event-components)
- IBM LEEF overview lists subsections "LEEF event components", "Predefined LEEF event attributes", "Custom event keys", "Custom event date format" (devTime attribute); it states LEEF is "a customized event format for QRadar" that any vendor may use; QRadar labels the first 25 Universal LEEF events "Unknown Log Event" until the log source is identified. — [IBM LEEF overview](https://www.ibm.com/docs/en/dsm?topic=leef-overview); [IBM LEEF format guide PDF](https://www.ibm.com/docs/en/SS42VS_DSM/com.ibm.dsm.doc/b_Leef_format_guide.pdf)
- ArcSight/OpenText "CEF Implementation Standard" (SmartConnectors 24.1) PDF: header `CEF:Version|Device Vendor|Device Product|Device Version|Device Event Class ID|Name|Severity|Extension`; text extraction of the PDF yields the sample line beginning `CEF:0|Security|threatmanager|1.0|100|worm…` and `CEF:0|security|threatmanager|1.0|100|detected a…` with escaping examples (pipe must be escaped in the header). — [CEF Implementation Standard PDF](https://www.microfocus.com/documentation/arcsight/arcsight-smartconnectors-24.1/pdfdoc/cef-implementation-standard/cef-implementation-standard.pdf); older 2017 "Common Event Format v25" mirror — [archive.org](https://archive.org/download/commoneventformatv25/CommonEventFormatV25.pdf)
- Elastic Common Schema: "an open source specification, developed with support from the Elastic user community"; current version 9.5.0; repo elastic/ecs is Apache-2.0, last push 2026-10-28. — [ECS reference](https://www.elastic.co/docs/reference/ecs); [GitHub API elastic/ecs](https://api.github.com/repos/elastic/ecs)
- OCSF schema browser shows version 1.9.0 (1.10.0-dev listed); categories System Activity [1], Findings [2], Identity & Access Management [3], Network Activity [4], Discovery [5], Application Activity [6], Remediation [7], Unmanned Systems [8]; classes include Authentication [3002], Network Activity [4001], HTTP Activity [4002]; repo ocsf/ocsf-schema is Apache-2.0, last push 2026-10-30. — [schema.ocsf.io](https://schema.ocsf.io/); [GitHub API ocsf/ocsf-schema](https://api.github.com/repos/ocsf/ocsf-schema)

### Inferences
- For labs, the IBM examples are sufficient as unit-test fixtures (header, tab-separated attributes, predefined keys `src`, `dst`, `srcPort`, `dstPort`, `usrName`, `sev`, `cat`, `devTime`). Learners can validate their LEEF emitter by round-tripping these lines; there is no need for a large LEEF corpus because LEEF is the target format, not the input.
- OCSF Authentication [3002] and HTTP Activity [4002] map naturally onto the auth.log and access-log datasets above; ECS is the lighter target for pandas users.

### Gaps
- No public file collection of QRadar DSM "sample events" or LEEF-formatted logs from real devices was found in this search; IBM DSM configuration pages per vendor may include single examples but were not enumerated.
- The CEF PDF's revision date could not be extracted (text extraction returned fragments only); the SmartConnectors 24.1 URL implies a 2024 edition.

- Zeek's own test-suite traces (zeek-testing) were not enumerated.
