## 1. BLUF

**Elastic Stack ระดับ "Free and open - Basic" ให้ "วงจรหลัก" ของ SIEM ครบโดยไม่เสียเงิน**: Fleet/Elastic Agent + integration package (422 package สำหรับ Kibana 9.2.0 ทุกตัวที่ตรวจประกาศ `subscription: basic`), ingest pipeline/ECS, detection engine ครบ 6 ใน 7 ประเภท rule (custom query, EQL `sequence`, threshold, indicator match, new terms, ES|QL — ขาดเฉพาะ machine learning), prebuilt rule "over 1,000" พร้อม import/export, Timelines, Cases, ILM/data stream/SLM/snapshot, Lens/dashboards/CSV export, Entity Store, Osquery Manager, ATT&CK coverage page และ connector แบบ Index + Server log ([Elastic subscriptions](https://www.elastic.co/subscriptions) [OFFICIAL]) **สิ่งที่ Basic ทำไม่ได้** แบ่งเป็นสองกลุ่ม: กลุ่ม "ตัดขาดกับโลกภายนอก" คือ connector แจ้งเตือน email/Slack/webhook/Jira/ServiceNow (Gold+), Watcher (Gold+), PDF/PNG report (Gold+), audit logging (Gold+) และกลุ่ม "ขั้นสูง" คือ alert suppression, ML anomaly detection, Entity risk score, host isolation, SSO, field-level security (Platinum+) รวมถึงการแก้ prebuilt rule ในที่, Attack Discovery, AI Assistant, Automatic Import, Automatic Migration (Enterprise) และเพราะ Elastic ระบุเองว่า Gold และ Platinum "no longer available for new customers" ทางเลือกจริงสำหรับผู้ซื้อใหม่แบบ self-managed จึงเหลือ **Basic (ฟรี) หรือ Enterprise** ([Elastic subscriptions](https://www.elastic.co/subscriptions) [OFFICIAL]) **เวอร์ชันที่ควร pin คือ 9.5.5** (หน้า download ระบุ 9.5.5 ปล่อย 6 ต.ค. 2026 ขณะที่เอกสาร Docker ใช้ 9.5.6 เป็นตัวอย่าง; image อย่างเป็นทางการมี arm64 สำหรับ Apple Silicon) ([Elasticsearch downloads](https://www.elastic.co/downloads/elasticsearch); [Docker Hub elasticsearch tags](https://hub.docker.com/v2/repositories/elastic/elasticsearch/tags/?name=9.) [OFFICIAL]) **RAM**: Elastic กำหนดขั้นต่ำเพียง "allocate at least 4GB of memory to Docker Desktop" และให้ heap ปรับอัตโนมัติจาก memory limit ของ container ([Install Elasticsearch with Docker](https://www.elastic.co/docs/deploy-manage/deploy/self-managed/install-elasticsearch-docker-basic) [OFFICIAL]); บนเครื่อง 36 GB ที่ Docker Desktop ให้ VM ครึ่งหนึ่งของ host โดย default งบที่พอเหลือเฟือคือ ES 8 GB (heap ≈ 4 GB), Kibana 2 GB, Fleet Server 0.5 GB, agent 2 ตัวรวม 1 GB [INFERRED] องค์ประกอบของ QRadar ที่ **เทียบไม่ได้บน Basic ไม่ว่าจะเขียนไฟล์เก่งแค่ไหน** คือ offense ที่มี magnitude แบบ dynamic, UBA แบบ risk score และการแจ้งเตือนออกนอกระบบ — สามอย่างนี้ต้องย้ายไปอยู่ใน "ชั้น Python" ที่ poll alert index แล้วคำนวณ fingerprint/dedupe/score เอง ซึ่งเป็นสิ่งที่หลักสูตรนี้สอนอยู่แล้วในตัวอย่าง 7.1–7.4 สุดท้าย **"AI สร้าง SIEM" ในที่นี้หมายถึง Codex เขียนไฟล์ (compose, JSON, NDJSON, TOML, Python) แล้วยิง REST API** ไม่ใช่ AI feature ของ Elastic เอง ซึ่งล้วนเป็น Enterprise และไม่มีตัวเลข accuracy ที่เผยแพร่

## 4. Ingest blueprint: integration ฟรี 9 ตัว, LEEF ด้วย dissect+kv, EVTX ผ่าน evtx_dump

**Integration ที่ติดตั้งผ่าน Fleet API** (เวอร์ชันจาก EPR สำหรับ Kibana 9.2.0; ต้อง re-query ด้วย `kibana.version=9.5.5` ก่อนใช้จริง เพราะหน้า docs แสดงเวอร์ชันสูงกว่า เช่น system 3.3.0 ต้องการ Kibana ^9.2.1): `system` 2.7.2 (`system.auth`, `system.syslog` ผ่าน `logfile`/`journald`), `nginx` 3.2.2 (`nginx.access`, `nginx.error`), `windows` 3.12.1 (`windows.sysmon_operational`, `windows.powershell*`, `windows.forwarded`…), `winlog` 2.6.1 (channel ใด ๆ), `sysmon_linux` 1.9.1, `zeek` 5.0.1 (43 stream, ต้องเป็น JSON logs), `suricata` 2.27.1 (`suricata.eve`), `cef` 2.24.0 (UDP 9003/TCP 9004, มี `cef.extensions.*`), `udp` 2.4.0/`tcp` 2.2.0 (Custom UDP/TCP Logs มีสวิตช์ "Syslog Parsing" RFC 3164/5424 และช่อง "custom ingest pipeline"), `filestream` 2.3.3 (Custom Logs; ไฟล์ < 1024 byte ไม่ถูกอ่านจนกว่าจะปรับ "Fingerprint length") และ `syslog_router` 1.0.1 สำหรับจำลอง auto-detect ([EPR manifests เช่น system](https://epr.elastic.co/package/system/2.7.2), [cef](https://epr.elastic.co/package/cef/2.24.0), [zeek](https://epr.elastic.co/package/zeek/5.0.1), [suricata](https://epr.elastic.co/package/suricata/2.27.1), [udp](https://epr.elastic.co/package/udp/2.4.0), [filestream](https://epr.elastic.co/package/filestream/2.3.3); [Custom UDP Logs docs](https://www.elastic.co/docs/reference/integrations/udp); [Custom Logs (Filestream)](https://www.elastic.co/docs/reference/integrations/filestream) [OFFICIAL]) ติดตั้งด้วย `POST /api/fleet/epm/packages/{pkgName}/{pkgVersion}` แล้วสร้าง `package_policies` โดย body `inputs` ต้องคัดลอกจากแท็บ "API reference"/"Preview API request" ของแต่ละ integration ใน Kibana เพราะโครง `inputs` ต่างกันทุก package ([Kibana Fleet APIs](https://www.elastic.co/docs/reference/fleet/fleet-api-docs) [OFFICIAL]) Wazuh ไม่มี package: ถือ `alerts.json` เป็น NDJSON ผ่าน Custom Logs (Filestream) [INFERRED]

**LEEF ไม่มี integration — เขียน pipeline เอง.** การค้นทั้ง EPR, `elastic/integrations`, `elastic/beats`, หน้า `decode_cef` และ ingest processor reference ยืนยันว่าไม่มี LEEF ที่ใดเลย ([EPR search](https://epr.elastic.co/search?all=false); [decode_cef processor](https://www.elastic.co/docs/reference/fleet/decode_cef-processor); [Ingest processor reference](https://www.elastic.co/docs/reference/enrich-processor) [OFFICIAL]) โครง LEEF ตาม IBM คือ `[syslog header] LEEF:Version|Vendor|Product|Version|EventID|[Delimiter|]key=value<TAB>key=value…` โดย LEEF 2.0 ระบุ delimiter ได้ (เช่น `^`, `x5E`, `x7c`) และ attribute ที่ QRadar normalize ได้แก่ `src`, `dst`, `sev`, `cat`, `devTime`/`devTimeFormat`, `srcPort`/`dstPort`, `usrName`, `proto` ([IBM LEEF components](https://www.ibm.com/docs/en/SS42VS_DSM/com.ibm.dsm.doc/c_LEEF_Format_Guide_LEEFeventcomps.html); [IBM predefined attributes](https://www.ibm.com/docs/en/SS42VS_DSM/com.ibm.dsm.doc/c_LEEF_Format_Guide_predefinedAttrrs.html) [OFFICIAL]) pipeline `logs-lab.leef@custom` จึงมีลำดับ `dissect` header ด้วย pattern `%{syslog_pri}%{syslog_ts} %{syslog_host} LEEF:%{leef.version}|%{leef.vendor}|%{leef.product}|%{leef.product_version}|%{leef.event_id}|%{leef.attrs}` → `kv` บน `leef.attrs` (`field_split: "\t"`, `value_split: "="`, `target_field: leef.ext`) → `rename` `leef.ext.src→source.ip`, `dst→destination.ip`, `srcPort→source.port`, `dstPort→destination.port`, `usrName→user.name`, `sev→event.severity` → `date` จาก `devTime` (epoch 13 หลักไม่ต้อง `devTimeFormat`) → `set` `event.kind: event`, `ecs.version: 9.5.0`, เก็บ `event.original` และ `on_failure` เขียน `error.message` (รูปแบบ dissect+kv เป็นข้อเสนอของทีม [INFERRED]; **Offline EVTX บน macOS.** Winlogbeat อ่าน `.evtx` ที่ archive ได้ ("Yes, Winlogbeat can ingest archived .evtx files") แต่เป็น "Windows service" ที่ติดตั้งผ่าน PowerShell เท่านั้น ([Winlogbeat reading from .evtx](https://www.elastic.co/docs/reference/beats/winlogbeat/reading-from-evtx); [winlogbeat README](https://github.com/elastic/beats/blob/main/winlogbeat/README.md) [OFFICIAL]) เส้นทางบน macOS คือ `evtx_dump -o jsonl Security.evtx > security.jsonl` (Rust, prebuilt macOS binary, Apache-2.0/MIT) หรือ `pyevtx-rs`/`python-evtx` แล้ว bulk ผ่าน `helpers.streaming_bulk` ของ elasticsearch-py โดยระบุ `pipeline` และ `_op_type: create` ลง data stream ([omerbenamram/evtx](https://github.com/omerbenamram/evtx); [python-evtx](https://github.com/williballenthin/python-evtx); [Python client helpers](https://www.elastic.co/docs/reference/elasticsearch/clients/python/client-helpers) [SECONDARY/OFFICIAL]) ข้อควรระวังสำคัญ: โครง field จาก `evtx_dump` (`Event.System.*`, `Event.EventData.*`) **ต่างจาก** `winlog.event_data.*` ของ Winlogbeat ดังนั้น pipeline ของ Windows integration จะไม่ apply ตรง ๆ ต้องมี pipeline reshaping ก่อน [INFERRED] Hayabusa/Chainsaw ให้ JSONL เช่นกันแต่เป็น "findings" (Sigma hit) ไม่ใช่ raw telemetry จึงเหมาะกับการสอน detection มากกว่า normalization ([hayabusa](https://github.com/Yamato-Security/hayabusa); [chainsaw](https://github.com/WithSecureLabs/chainsaw) [SECONDARY]) corpus EVTX ที่รายงาน dataset เลือกคือ mdecrevoisier/EVTX-to-MITRE-Attack (CC0, 293 ไฟล์)

**รูปแบบ `@custom` และการตรวจสอบ.** Fleet ต่อท้ายทุก integration pipeline ด้วย `pipeline` processor สี่ตัวตามลำดับ `global@custom` → `logs@custom` → `logs-<package>.integration@custom` → `logs-<dataset>@custom` ทุกตัวมี `ignore_missing_pipeline: true` และคำเตือนของ Elastic คือ "Left unchanged, that call does nothing. You can modify the call to create custom pipelines that persist across upgrades" ([Kibana helpers.ts](https://github.com/elastic/kibana/blob/main/x-pack/platform/plugins/shared/fleet/server/services/epm/elasticsearch/ingest_pipeline/helpers.ts); [Ingest pipelines](https://www.elastic.co/docs/manage-data/ingest/transform-enrich/ingest-pipelines) [OFFICIAL]) นี่คือ "DSM Editor/Log Source Extension" ของ Elastic: แก้ผลลัพธ์ของ vendor parser โดยไม่แตะตัว parser [INFERRED] mapping เพิ่มใส่ component template `logs@custom`, `<data_stream>@custom`, `<package>@custom` (9.1) หรือ `<namespace>@custom` (9.5) โดย "later entries take precedence" ([Fleet data streams](https://www.elastic.co/docs/reference/fleet/data-streams) [OFFICIAL]) การตรวจก่อน index ใช้ `POST _ingest/pipeline/_simulate` ที่ส่ง `docs[]` พร้อม `_source` และได้เอกสารที่แปลงแล้วกลับมา ส่วนหลัง index ใช้ `GET logs-*-lab/_search` กับ `"fields": [...]`, `"_source": false` ซึ่ง Elastic แนะนำเหนือ `_source` filtering เพราะ "returns values in the way that matches how Elasticsearch indexes them" ([Simulate pipeline API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-ingest-simulate); [Retrieve selected fields](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrieve-selected-fields) [OFFICIAL]) ใช้ namespace `lab` ทุก data stream (`logs-nginx.access-lab`) เพื่อให้ลบ `logs-*-lab` ได้โดยไม่กระทบอื่น และเพื่อผูก ILM สั้นผ่าน `<namespace>@custom` [INFERRED] เมื่อ bulk ตรงโดยไม่ผ่าน agent ต้องใส่ `data_stream.type/dataset/namespace` เองและใช้ action `create` เท่านั้น ("Data streams support only the `create` action") ([Bulk API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-bulk) [OFFICIAL])

## 5. Detection/correlation blueprint: 1,000+ prebuilt rule ฟรี แต่ offense ต้องเขียนเองใน Python

**Prebuilt rules.** `PUT /api/detection_engine/rules/prepackaged` ติดตั้ง/อัปเดต rule และ Timeline ทั้งหมด (response `rules_installed`, `rules_updated`) และ `GET …/prepackaged/_status` บอกจำนวน installed/available/outdated; Elastic ปล่อยอัปเดต "biweekly" และย้ำว่า "enabling them all at once can lead to alert fatigue" จึง enable ตาม tag ด้วย `_bulk_action {"action":"enable","query":"alert.attributes.tags: \"OS: Linux\""}` (รูปแบบค่า tag ต้องยืนยันจาก `GET /api/detection_engine/tags`) ([Install prebuilt rules API](https://www.elastic.co/docs/api/doc/kibana/operation/operation-installprebuiltrulesandtimelines.md); [Install and manage prebuilt rules](https://www.elastic.co/docs/solutions/security/detect-and-alert/install-manage-elastic-prebuilt-rules) [OFFICIAL]; tag format [INFERRED]) บน Basic prebuilt rule เป็น read-only ("prebuilt Elastic rules on a Basic subscription, ca[nnot be edited]") แต่ duplicate แล้วแก้สำเนาได้ทุก tier ([Bulk action API](https://www.elastic.co/docs/api/doc/kibana/operation/operation-performrulesbulkaction) [OFFICIAL])

**Rule as code จากสองแหล่ง.** (ก) repo `elastic/detection-rules` (ELv2; 2,318 TOML ใน `rules/` + 131 ใน `rules_building_block/`; Python 3.12+) มี CLI `export-rules-from-repo -o rules.ndjson` ที่ "Export rule(s) and exception(s) into an importable ndjson file" และ `kibana import-rules -f <rule.toml>` โดย Kibana auth ใช้ `api_key` เท่านั้น ([detection-rules README](https://github.com/elastic/detection-rules); [CLI.md](https://github.com/elastic/detection-rules/blob/main/CLI.md) [OFFICIAL]) (ข) Sigma: `pySigma-backend-elasticsearch` 2.1.1 (LGPL-3.0, 2026-08-10) แปลงเป็น Lucene/EQL/ES|QL และสร้าง `siem_rule_ndjson` ได้ตรง (`-t lucene -p lucene-kibana-siemrule.yml`, `-t eql -p eql-siemrule-ndjson.yml`, `-t esql -p esql-siemrule-ndjson.yml`) กับ pipeline `ecs_windows`, `ecs_zeek_beats` ([pySigma-backend-elasticsearch](https://github.com/SigmaHQ/pySigma-backend-elasticsearch) [SECONDARY]) ทั้งสองทางลงเอยที่ `POST /api/detection_engine/rules/_import?overwrite=true` แบบ multipart `file=@rules.ndjson` ([Import rules API](https://www.elastic.co/docs/api/doc/kibana/operation/operation-importrules) [OFFICIAL]) หลักสูตรนี้ได้เปรียบตรงที่ rule เดียวกันแปลงเป็น AQL ด้วย `sigma convert -t ibm-qradar-aql -p qradar-aql-payload` ได้ (backend ของ IBM, MIT) จึงสอน "same detection, two SIEMs" ได้จริง ([IBM/pySigma-backend-QRadar-AQL](https://github.com/IBM/pySigma-backend-QRadar-AQL) [OFFICIAL])

**EQL sequence แทน correlation rule.** EQL `sequence by host.id with maxspan=5m [process where …] [process where …]` รองรับ `until`, `with runs=N` (1–100), missing-event `![…]` และ `sample by` แต่ "You cannot use EQL comparison operators to compare a field to another field", ไม่มี join, ไม่มี `count`/`unique_count` และ pending-state overwrite ทำให้ "do not find all possible matches" ([EQL syntax](https://www.elastic.co/docs/reference/query-languages/eql/eql-syntax) [OFFICIAL]) correlation แบบนับ (brute force N ครั้ง) ใช้ threshold rule; correlation ข้าม rule ใช้ building-block rule (ซ่อนจาก UI) แล้วเขียน rule ชั้นสองที่มี index pattern `.alerts-security.alerts-*` ([Building block rules](https://www.elastic.co/docs/solutions/security/detect-and-alert/about-building-block-rules) [OFFICIAL])

**Cases อัตโนมัติและข้อจำกัด.** Cases connector "creates Cases in Kibana when alerts occur", จัดกลุ่มด้วย field ได้ (unique case ต่อ group), alert ใหม่เข้าร่วม case เดิมเฉพาะ "within a 7 day time window", มีได้หนึ่ง action ต่อ rule และ **สร้างไม่ได้ผ่าน Stack Management หรือ API** ([Cases connector](https://www.elastic.co/docs/reference/kibana/connectors-kibana/cases-action-type) [OFFICIAL]) Case management เป็น Basic แต่ "Case user assignment" เป็น Platinum+ ([Subscriptions](https://www.elastic.co/subscriptions) [OFFICIAL])

**สิ่งที่ตรงกับ offense/magnitude ไม่ได้บน Basic — และ workaround.** QRadar offense ถูก chain ด้วย "Index offense based on" ข้าม rule โดยอัตโนมัติ มี magnitude ที่คำนวณจาก relevance/severity/credibility และ "re-evaluated when new events are added to the offense and also at scheduled intervals" และมี lifecycle active → dormant (30 นาที) → inactive (5 วัน) → retention 30 วัน ([IBM offense indexing](https://www.ibm.com/docs/en/SSKMKU/com.ibm.qradar.doc/c_qradar_ug_offense_indexing.html); [IBM offense prioritization](https://www.ibm.com/docs/en/qsip/7.5?topic=management-offense-prioritization); [IBM offense retention](https://www.ibm.com/docs/en/SSKMKU/com.ibm.qradar.doc/c_qradar_Off_Retention.html) [OFFICIAL]) ฝั่ง Elastic alert มี `kibana.alert.risk_score` คงที่ต่อ rule (override ได้จาก source field), status แค่ open/acknowledged/closed และ Entity risk score ที่ใกล้ magnitude ที่สุด (0–100, รายชั่วโมง, ถ่วงด้วย asset criticality 0.5–2) เป็น Platinum+ ([Create rule API](https://www.elastic.co/docs/api/doc/kibana/operation/operation-createrule.md); [Entity risk scoring](https://www.elastic.co/docs/solutions/security/advanced-entity-analytics/entity-risk-scoring) [OFFICIAL]) **ชั้น Python** ที่หลักสูตรมีอยู่แล้วปิดช่องว่างนี้ตรงตัว: ตัวอย่าง 7.3 อ่าน `.alerts-security.alerts-default` ด้วย `fields` + filter `kibana.alert.workflow_status: open`; ตัวอย่าง 7.2 คำนวณ `fingerprint = sha256(rule_id|host|user|src_ip)` ใน sliding window 10 นาที แล้ว `risk_score = base(severity) + 8×asset_crit + 15×ti_hits + burst bonus − 25×FP rate` คั่น route เป็น merge/auto-close/queue/escalate; ตัวอย่าง 7.1 ห่อเป็น OCSF Detection Finding (class_uid 2004) และ 7.4 เปิด/อัปเดต Jira ticket ด้วย label `fp-<fingerprint>` (ดู `docs/python-security-automation-research.md` §7) ผลลัพธ์เขียนลง index `offenses-lab` ที่มี field ล้อ `GET /siem/offenses` ของ QRadar (`magnitude`, `event_count`, `start_time`, `last_updated_time`, `status`, `rules[]`) ตามรายงาน dataset ก่อนหน้า — นี่คือ "offense" ของ lab และเป็นสิ่งเดียวที่ทำให้ตาราง QRadar ↔ Elastic ครบ [INFERRED]

**Alert index, API และการแจ้งเตือน.** alert อยู่ใน hidden index `.alerts-security.alerts-<space-id>` มี `kibana.alert.rule.name/uuid`, `severity`, `risk_score`, `workflow_status`, `workflow_tags`, `suppression.docs_count`, `rule.threat.*`, `building_block_type`, `original_time` ([Alert schema](https://www.elastic.co/docs/reference/security/fields-and-object-schemas/alert-schema) [OFFICIAL]) ปิด alert ด้วย `POST /api/detection_engine/signals/status {"signal_ids":[…],"status":"closed","reason":"false_positive"}` ([Set alert status](https://www.elastic.co/docs/api/doc/kibana/operation/operation-setalertsstatus.md) [OFFICIAL]) ข้อจำกัดที่คมที่สุดของ Basic คือ connector: มีแค่ "Elastic Connectors (e.g., Server Log and Index)" ส่วน email/webhook/Slack/Jira/ServiceNow/TheHive/XSOAR เป็น Gold+ และ "Detection alert external actions" ก็ไม่อยู่ใน Basic ([Subscriptions](https://www.elastic.co/subscriptions) [OFFICIAL]) ทางออกฟรีคือ (ก) Index connector เขียน alert ลง index ที่ script นอกอ่าน หรือ (ข) Python poll alert index/`signals/search` ทุก 1–5 นาทีแล้วส่ง Jira/Slack เอง ซึ่งคือตัวอย่าง 7.3 + 7.4 [INFERRED] ทีมค้นคว้าสรุปว่าเส้นแบ่ง free/paid ที่คมที่สุด "sharper than the rule types themselves" อยู่ตรงนี้

**ATT&CK coverage.** หน้า "MITRE ATT&CK coverage" แสดง rule ที่ติดตั้ง/enabled ต่อ tactic/technique, ปุ่ม "Enable all disabled", กรอง Elastic/Custom และใช้ ATT&CK v19.1 ตั้งแต่ 9.5.0 (v19 ยุบ Defense Evasion เป็น Stealth + Defense Impairment จึงต้อง remap custom rule) ([ATT&CK coverage](https://www.elastic.co/docs/solutions/security/detect-and-alert/mitre-attandckr-coverage) [OFFICIAL]) ไม่มีแถว tier ในหน้า subscriptions และเอกสารไม่ระบุ จึง "no gating found" [INFERRED] Navigator layer สร้างจาก `threat[]` ของ rule ตามแบบ `navigator.py` (`domain: enterprise-attack`, `versions.layer 4.4`, `score` = จำนวน rule) และ `detection_rules dev attack convert-threat-mappings -t 19 --dry-run` ช่วย remap ([navigator.py](https://raw.githubusercontent.com/elastic/detection-rules/main/detection_rules/navigator.py); [CLI.md](https://github.com/elastic/detection-rules/blob/main/CLI.md) [OFFICIAL]) เทียบกับ QRadar Use Case Manager ที่ export JSON เข้า Navigator ได้และมี `GET /api/mappings` ([IBM UCM APIs](https://www.ibm.com/docs/en/SS42VS_SHR/com.ibm.tuningapp.doc/r_available_apis.html) [OFFICIAL]) ทั้งสองให้ visibility ใกล้กัน ต่างที่ Elastic เก็บ mapping ใน JSON ของ rule เองซึ่ง Codex สร้างออฟไลน์ได้

## 7. "AI ทำได้" หมายถึงอะไรจริง ๆ: Codex เขียนไฟล์ ไม่ใช่ AI ของ Elastic

Elastic มี AI feature ที่ตรงกับคำว่า "AI สร้าง SIEM" อยู่สี่ตัว และ **ทั้งหมดเป็น Enterprise** บน Elastic Stack: **Automatic Import** "uses a large language model (LLM) with specialized instructions to analyze source data and generate a custom integration" จาก JSON/NDJSON/CSV/syslog, รับสูงสุด 1,000 sample หรือ 10 MB (9.4+; 9.0–9.3 ส่งแค่ 100 sample แรก), มีขั้น "Review & approve" ให้คนแก้ pipeline และเตือนว่าข้อมูลที่ส่งไป LLM ภายนอก "can be used to train the models" โดย**ไม่มีตัวเลข accuracy ใด ๆ** ([Automatic Import](https://www.elastic.co/docs/explore-analyze/ai-features/automatic-import) [OFFICIAL]) **AI Assistant** (สร้าง ES|QL, สรุป alert, แก้ rule query) ต้องการ "An Enterprise subscription" และ LLM connector ([AI Assistant](https://www.elastic.co/docs/solutions/security/ai/ai-assistant) [OFFICIAL]) **Attack Discovery** จับกลุ่ม alert เป็น attack narrative พร้อม MITRE mapping (เอกสาร 8.19 บอก default 100 alert จาก 24 ชั่วโมง) และอยู่ในแถว Enterprise ของหน้า subscriptions ([Attack Discovery](https://www.elastic.co/docs/solutions/security/ai/attack-discovery); [Subscriptions](https://www.elastic.co/subscriptions) [OFFICIAL]) **Automatic Migration** แปล rule จาก Splunk/QRadar/Sentinel เป็น Elastic rule; QRadar rule GA ตั้งแต่ 9.4 (Event/Flow/Common rule จาก XML export, คิด building block ด้วย, reference set ลง lookup index) แต่ "QRadar dashboards not supported" และต้องมี Enterprise + ML enabled ([Automatic Migration](https://www.elastic.co/docs/solutions/security/get-started/automatic-migration); [From QRadar to Elastic](https://www.elastic.co/security-labs/from-qradar-to-elastic) [OFFICIAL]) ทั้งหมดใช้ได้ระหว่าง trial 30 วัน (start-local และ docker-elk เริ่มด้วย trial) จึงเหมาะเป็น demo ของผู้สอนแต่ไม่ใช่ฐานของแบบฝึกหัด [INFERRED]

สิ่งที่หลักสูตรนี้เรียกว่า "AI สร้าง" จึงเป็นอีกกลไกหนึ่ง: **Codex เขียนไฟล์** (compose, pipeline JSON, rule NDJSON/TOML, saved-object NDJSON, Python) แล้วยิง REST API ที่เป็น Basic ทั้งหมด ซึ่งโครงสร้างเดียวกับที่ Elastic เองทำใน Automatic Import ("LLM เขียน ingest pipeline + ECS mapping, คนตรวจ") แต่รันนอกผลิตภัณฑ์ Elastic สนับสนุนแนวนี้อย่างเป็นทางการผ่าน **elastic/integration-skills** (Apache-2.0, "Beta — This is the initial release", 16 ดาว, push 2026-10-30) ที่ให้ skill `/research-integration` และ `/create-integration` สำหรับ "Cursor, Claude Code, Codex" โดยต้องมี Docker, `elastic-package` และ Go tool อีกชุด ([integration-skills README](https://github.com/elastic/integration-skills) [OFFICIAL]) harness ทดสอบที่เหมาะกับ Codex คือ `elastic-package test pipeline` ที่อ่าน `_dev/test/pipeline/test-*.log` + `*-expected.json` และ `--generate` เขียน expected ให้ ("It cannot know if this is actually correct") ([Pipeline testing](https://www.elastic.co/docs/extend/integrations/pipeline-testing) [OFFICIAL]) ความจริงที่ต้องบอกผู้เรียนตรง ๆ: **ไม่มีตัวเลข accuracy/precision ของ Automatic Import, Attack Discovery หรือ Automatic Migration จาก Elastic หรือบุคคลที่สาม** และไม่มีของ Codex ด้วย ดังนั้น pass criteria ทุก ticket ต้องเป็นสิ่งที่ API ยืนยันได้ ไม่ใช่ความเชื่อว่า AI ทำถูก

## 8. หลักฐานเปรียบเทียบ: analyst ให้ Elastic เป็น Visionary/Leader แต่ไม่มีใครวัด Elastic vs QRadar ตรง ๆ

**Ingest และ parsing.** Elastic ไม่เผยแพร่จำนวน integration รวม — 422/510/508 เป็น query ของทีม; field list ECS ต่อ integration ถูกตัดบนหน้า docs (ต้องอ่าน EPR `data_streams[].fields`); หน้า API reference "install package" คืน 404 จึงยืนยันได้แค่ route constant; พอร์ต syslog default ของ FortiGate/PAN-OS ไม่ครบ; ไม่พบหน้า Elastic ที่เปรียบเทียบ performance ingest pipeline vs Logstash; route ใน Fleet UI สำหรับผูก custom pipeline ไม่ได้บันทึกตรงตัว; license ของ `elastic-package` ไม่ได้ตรวจ; หน้า ecs-logging คืน 404 (รายการภาษาเป็นความรู้เดิม ไม่ยืนยัน); ไม่มีคำแถลงว่า ECS จะ freeze เพื่อ OTel เมื่อใด; ไม่มีขั้นตอนที่ Elastic รองรับสำหรับ `.evtx` → Elasticsearch บน macOS/Linux (ทุกทางเป็น third-party); ไม่ได้ตรวจ `evtx2es` กับ client 9.x; flag ของ Hayabusa เวอร์ชันปัจจุบันไม่ได้ตรวจ; ชื่อ ILM policy default (`logs` หรือ `logs@lifecycle`) ไม่ปรากฏบนหน้าที่ดึง; ข้อจำกัดอักขระ/ความยาวของ dataset นอกจาก "no `-`" ไม่พบ; ไม่มีการเปรียบเทียบเชิงเทคนิค Elastic-vs-QRadar-DSM จาก Elastic, IBM หรือบุคคลที่สาม (ตารางประกอบเอง); หน้า event pipeline ของ IBM (Collector → parsing → QID → coalescing → Processor) ไม่ได้ดึง; IBM ไม่เผยแพร่จำนวน DSM เป็นตัวเลข (396 แถว HTML เป็นการนับเอง); หน้า QID/category taxonomy ไม่ได้ดึง

**Detection, correlation, coverage.** หน้า Create-rule API ถูกตัด: default ของ `from` (เอกสารเก่า `now-6m`), sub-field `alert_suppression`, `actions.frequency` ไม่ได้อ่านจากหน้า 9.x; ค่า default `securitySolution:defaultAnomalyScore` และรายการ prebuilt ML job ไม่อยู่บนหน้าที่ดึง; ไม่ได้นับ rule ต่อประเภท (EQL vs ES|QL); `kbn-xsrf` บน Detections API ไม่ได้ยืนยันจากหน้า operation ที่ดึง (ยืนยันจาก OpenAPI bundle และหน้า Reporting); ไม่มีหน้า vendor ระบุ cap ของ Attack Discovery ใน 9.x (มีแต่ 8.16/8.19); สูตรถ่วงน้ำหนัก magnitude และความยาว "scheduled intervals" ของ IBM ไม่เผยแพร่; dormant 5 วันปรับได้หรือไม่มีแต่ community thread; ไม่พบหน้า IBM ของ `REFERENCESETCONTAINS` (มีแต่ตัวอย่าง `REFERENCEMAP`/`REFERENCETABLE` และ community); README ของ pySigma Elasticsearch backend ไม่ระบุชื่อ class `ESQLBackend`/`EQLBackend`; tier ของหน้า ATT&CK coverage ไม่ระบุที่ใด; Navigator-JSON export ของ UCM ยืนยันจาก Juniper mirror ไม่ใช่ ibm.com; ความหมายของแถว "Threat intelligence management" ไม่ได้นิยาม; พฤติกรรม transform `*_latest` ของ TI integration ตรวจเฉพาะ Anomali; เอกสาร X-Force Exchange/MISP importer ของ QRadar ไม่ได้ดึง; หน้า alert schema อ่านถึง ~100k ตัวอักษร field ท้าย ๆ ไม่ได้อ่าน; tier ของ alert assignment (ไม่ใช่ case) และ Osquery in-rule response action ไม่ระบุ; ไม่ได้ค้นว่าเขียน `kibana.alert.*` จากภายนอก detection engine ได้หรือไม่; ชื่อ export type `csv_searchsource`/`csv_v2`/`pngV2` และ default `xpack.reporting.csv.maxSizeBytes` ไม่พบ; tier ของ scheduled report (นอกจาก PDF/PNG Gold+) ไม่ระบุ; หน้า Security Overview/Detections dashboard ไม่ได้ดึง

**Precedents, IaC, AI, sizing.** ไม่พบ memory requirement ของ wazuh single-node นอกจาก heap 1 GiB ใน compose (หน้า Prerequisites ดึงไม่ได้); elastdocker มี Fleet Server หรือไม่ยืนยันแค่จาก grep README; ไม่มีข้อมูลการใช้ peasead/elastic-container บน Apple Silicon (GitHub issue search ได้ 0); หน้า hardware Security Onion 3.x ไม่ระบุเวอร์ชัน; หน้า Terraform Registry ดึงไม่ได้จึงไม่ยืนยันเลข registry version ปัจจุบัน (resource list จาก branch main); หน้า API reference ของ saved-objects import คืน 404 (`createNewCopies` ยืนยันจาก OpenAPI bundle เท่านั้น); ไม่พบ benchmark อิสระหรือ peer-reviewed เทียบ Elastic กับ QRadar ด้าน parsing/offense/UEBA (Gartner Peer Insights คืน 403, PeerSpot เป็น aggregator); ไม่มีจำนวน DSM ของ QRadar หรือ integration ด้าน security ของ Elastic อย่างเป็นทางการ; ไม่พบ SANS paper เรื่อง ELK-as-SIEM; **ไม่มีข้อมูล accuracy/precision ของ Automatic Import, Attack Discovery, Automatic Migration จาก Elastic หรือบุคคลที่สาม**; หน้า Attack Discovery ปัจจุบันไม่ระบุ tier (ใช้ตาราง subscriptions); tier ของ ML rule มาจากตาราง ไม่ใช่ข้อความ; ไม่มีรายงาน/benchmark ของ Elastic 8/9 (รวม Fleet Server, Defend) บน Apple Silicon Docker Desktop (มีแค่ multi-arch tag และ anecdote); Elastic ไม่ระบุขั้นต่ำสำหรับ container Kibana/Fleet Server; claim ของ docker-elk ว่า Docker Desktop for Mac default 2 GB ขัดกับเอกสาร Docker ปัจจุบัน (50% ของ host) **เพิ่มเติมจากการสังเคราะห์:** arm64 tag ของ elastic-agent 9.5.5 ไม่ได้ยืนยัน (เห็นเพียง 9.4.9); เวอร์ชัน package ในตารางเป็นของ Kibana 9.2.0 ไม่ใช่ 9.5.5; ข้อกำหนด 90 วันตาม พ.ร.บ. คอมพิวเตอร์ไม่ได้ตรวจตัวบท; pass criteria ทุกข้อใน §9 เป็นข้อเสนอที่ยังไม่ได้รันจริง

## บทสรุป

สิ่งที่เปลี่ยนไปจากภาพจำ "ELK ไม่ใช่ SIEM" คือฝั่ง *ingest และ detect* ของ Elastic Basic ปี 2026 ไม่ได้เป็นรอง QRadar อีกแล้ว — 422 integration ที่ประกาศ `basic` ครอบคลุม Zeek/Suricata ที่ DSM list ไม่มี, rule 1,000+ ตัวติด ATT&CK มาในตัว, EQL `sequence` และ ES|QL `LOOKUP JOIN` ให้ correlation และ reference-list lookup ฟรี และทุกอย่างเป็นไฟล์ที่ agent เขียนและ API ตรวจได้ ช่องว่างที่เหลือรวมศูนย์อยู่ที่ *หลัง* alert: ไม่มี offense ที่ chain ข้าม rule, ไม่มี magnitude ที่ re-evaluate, ไม่มี UBA risk score และไม่มีทางส่งแจ้งเตือนออกนอกระบบโดยไม่จ่าย Enterprise ความบังเอิญที่เป็นประโยชน์คือช่องว่างเหล่านี้คือสิ่งที่หลักสูตร Python สอนอยู่แล้ว (normalize → fingerprint → score → route) ดังนั้น "Elastic Basic + ชั้น Python ของผู้เรียน" ไม่ใช่การประนีประนอม แต่เป็นสถาปัตยกรรมที่ทำให้ผู้เรียนเห็นว่า offense ของ QRadar ถูกคำนวณจากอะไรจริง ๆ

สองสิ่งที่ต้องสื่อสารกับผู้เรียน NT อย่างตรงไปตรงมา: หนึ่ง เส้นแบ่ง free/paid ของ Elastic ไม่ได้อยู่ที่ความสามารถตรวจจับแต่อยู่ที่ *การเชื่อมต่อกับโลกภายนอกและการตรวจสอบย้อนหลัง* (connector, audit log, support) ซึ่งเป็นเหตุผลที่ production SOC ยังเลือกจ่ายให้ QRadar หรือ Elastic Enterprise ไม่ใช่เพราะ Basic จับภัยไม่ได้; สอง ไม่มีใคร — ทั้ง Elastic, IBM, นักวิเคราะห์ หรือรายงานฉบับนี้ — มีตัวเลขว่า AI (ไม่ว่าจะเป็น Automatic Import หรือ Codex) สร้าง parser/rule ถูกกี่เปอร์เซ็นต์ ดังนั้นค่าของ ticket 15 ใบใน §9 ไม่ได้อยู่ที่ไฟล์ที่ Codex จะเขียน แต่อยู่ที่ pass criteria ที่ `_simulate`, `_search`, `signals/search` และ `_snapshot` ยืนยันได้ด้วยตัวเลข นั่นคือทักษะที่ย้ายไปใช้กับ QRadar 7.5/7.6 จริงใน NT cyfence ได้ทันทีโดยไม่ขึ้นกับว่าใครเขียนไฟล์
